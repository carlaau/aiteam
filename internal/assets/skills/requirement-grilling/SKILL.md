# 需求追问：把模糊需求问透，再交棒方案设计

brainstorming 回答「怎么做」（方案层），本技能回答「做什么、边界在哪」（需求层）。
需求没问透就做方案，方案拍得再认真也建在沙子上——brainstorming 拍板被后续推翻的案例，
多数是需求分支（排序规则/边界场景/业务语义）没穷举，不是方案选错。

**参考来源**：[mattpocock-skills-zh-CN](https://github.com/vinvcn/mattpocock-skills-zh-CN) 的 grilling 系访谈技能（grilling / grill-me / grill-with-docs），做了针对性改造：
修掉原版「多数决策只留在对话里」「收尾开放不指路」两个已知缺陷。

## 何时用本技能，何时跳过

**明确启用指令（用户说即加载，无条件进入）**：

- 「启用需求设计」「开始需求设计」「需求设计模式」
- 「需求分析」「启用需求分析」「做个需求分析」
- 「需要分析」「帮我分析下这个需求」「这个需求先分析下」

**命中任一判据 → 先走本技能再 brainstorming：**

1. 新功能域 / 没有先例可参照的交互形态
2. 涉及业务规则或用户红线（金额计算、权限、审批规则、计费规则）
3. 需求描述含模糊词：「大概」「之类」「类似 xx」「先做着看」
4. 交互细节密集型功能（排序、边界、空态、联动、竞态场景多）

**需求明确 → 直接 brainstorming，别过度流程：**

bug 修复、按既定模式新增表/CRUD、有明确指标的性能优化、纯重构。

## 硬门槛

<HARD-GATE>
需求澄清文档落盘并经用户确认前，不得进入 brainstorming 方案设计，更不得写任何实现代码。
</HARD-GATE>

## 交互语言（强制）

**全程大白话**。用户是业务方不是程序员：禁用开发黑话（要说「生成订单」不说「触发
recalc」）；必须用术语时先给一句大白话解释；技术细节（表结构/函数/缓存）不该出现在
问题里——那是 facts，自己去查代码，不是问用户的话。

## 访谈机制（design tree + frontier 逐轮推进）

把需求建模成一棵**决策树**：每个决策分支挂在它下面的子决策。按**轮次**推进：

1. **frontier** = 前置决策已敲定、现在就能问的问题集合（不需要猜还没听到的答案）。
2. 每一轮问完整条 frontier：**每个问题编号、附你的推荐答案**（降低用户负担），等用户逐个裁定。
3. 用户回答会重塑树：已敲定的决策把 frontier 向外推，解锁下游问题。答案依赖本轮另一个
   未决问题的，留给更晚的轮次，不要抢跑。
4. **facts 与 decisions 分离**：代码/文档/数据库能回答的事实，自己去查（读源码、查
   项目文档、派 sub-agent），**绝不拿去问用户**；只有取舍类决策交给用户。facts 自查
   必查清单：**字典/枚举配置**（项目的种子数据或配置表——枚举值/类型/各类可配置项，
   防止把可配置的东西硬编码成交互设计）、**真实样本**（项目的业务样本目录或测试
   fixture——相关域有真实业务材料时先看样本再问，防凭想象建模）、领域现状文档、
   项目术语表。
5. **结束判据**：frontier 为空——决策树每个分支都访问过，**没有留下任何被默默假设的东西**。
   此话当真：把你自己「以为理所当然」的点列出来过一遍，它们就是最危险的隐形 frontier。

### 反前提追问（值来源穷举，必问）

需求涉及「引导用户输入某个值」时（填表单/敲参数/选选项），**必须先问这个值的来源**，
不许把「用户填」当前提：手填 / **字典或配置给默认** / 从已有数据派生 / 批量导入 / 沿用上一次值。
默认值可用则优先推荐「不问用户」。铁案：一个「新增商品时要用户手填规格」的设计被用户否决——
规格字典本可配默认值、后端直接预填，三轮方案却全在「怎么让用户更快敲键盘」里打转，
方向层错误在方案层无解。同类「用户敲键盘」动线（输入/选择/定位）都要过这道反前提。

每问的格式：

```
❓ Q3 - 排序规则（订单列表默认按什么排：
   A 下单时间倒序  B 状态优先  C 按金额降序）
➡️ 推荐 A（对齐现有列表页行为）
```

## 书写纪律（问的过程同步沉淀，对齐项目文档体系）

- **术语冲突检查**：用户用词与项目术语表冲突时立即指出（「术语表里 order 指
  售后工单，你这里说的 order 是不是指采购订单？」）。新术语敲定**当场**写入
  项目术语表，不批量攒到最后。
- **模糊术语锐化**：用户说「账户」「单子」这类过载词时，提出精确的项目术语二选一。
- **边界场景压力测试**：为关键概念发明探测边界的具体场景（「删了套餐带出的赠品行，
  手动添加的行跟着删还是留着？」），迫使用户把边界说死。
- **与代码交叉验证**：用户描述的行为与现有代码矛盾时指出并裁定以谁为准（代码>文档，
  但需求可以决定改代码）。
- **ADR 三道门**：难逆转 + 无上下文会令人意外 + 真实权衡，三者齐备才提议追加一条
  ADR 到项目的决策记录目录；缺任一就只进澄清文档。大多数决策不配 ADR，一场会话
  零 ADR 是正常的。

## 产出与收尾（修掉原版「只进对话」缺陷）

**每个轮次结束就把该轮问答写入落盘文档**（不是攒到结尾）：

`{{SPECS_DIR}}/YYYY-MM-DD-<topic>-需求分析.md`（`{{SPECS_DIR}}` = 项目的 spec 目录，
如 aiteam 体系的 `specs/<迭代>/`（与 spec/plan 同居的 spec 目录体系），以项目约定为准）

文档骨架：

```markdown
# <主题> 需求澄清记录
> 状态：进行中 / 已确认（用户拍板日期）
> 交棒：brainstorming（方案层以此为输入，跳过其澄清问题段）

## 分支清单（决策树终态）
| # | 分支/问题 | 推荐 | 用户裁定 | 影响的边界 |
|---|---|---|---|---|

## 边界场景裁定
（每个压力测试场景 + 用户答案）

## 明确不做（YAGNI）
（用户明确排除的，防止下游脑补回来）

## 沉淀
（新增术语 → 项目术语表；新 ADR → 项目决策记录；都没有就写「无」）
```

**上位规划语境（模块内功能任务）——产出升格为功能级 PRD**：

若本功能处于项目某模块的开发阶段内（见项目的模块规划目录），澄清文档收尾时追加一节并升格为该功能的
**功能级 PRD**（不再单独写 PRD）：

- **验收标准（AC）**：编号表，每条可验证（对齐模块 PRD 的 AC 风格）；骨架里的「明确不做」节即 PRD 边界节。

用户批准后，该 PRD 登进模块任务文档的功能清单（一行），后续 brainstorming/spec 以它为冻结输入。
维护类（轻通道）任务不升格，保持原样交棒 brainstorming。

**收尾动作**（frontier 空且用户确认共同理解后）：

1. 澄清文档状态改「已确认」，请用户过目一遍再定稿。
2. 提示交棒：**「需求已问透，进入方案设计」——调用 brainstorming 技能**，把澄清文档
   作为输入递给它（brainstorming 从方案探索段开始，跳过它自己的澄清提问）。
3. 本技能的终止状态是调用 brainstorming，与 brainstorming 终止于 writing-plans 串成完整链。

## 分寸

- 大白话提问，用户是业务方不是程序员；术语第一次出现给一句解释。
- 是访谈不是审讯：推荐答案先行，用户只需「对/不对/改这里」。
- 别把小需求 grill 成大项目：判据不命中就明确说「需求已清楚，直接进 brainstorming」
  并交棒——这个判断本身也是本技能的职责。
