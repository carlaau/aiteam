# aiteam 接入指南（多机多客户端配置）

aiteam 是一个单二进制：服务机上 `aiteam serve` 启动通讯中枢（HTTP 服务 + 内嵌 SQLite + 内嵌看板），各机器上的 AI 会话用同一个二进制的子命令作为 CLI 客户端接入。本指南覆盖：服务部署、配置、token、CLI 接入、双客户端示例、会话编制、看板、备份与故障语义。最短路径四步速览见仓库根 `README.md`。

---

## ① 服务部署

单二进制、零外部依赖（SQLite 内嵌，无 DB 实例、无初始化脚本），部署三步：

```bash
# 1. 拷贝：把 aiteam 二进制放到服务机任一空目录
#    （发布页下载对应平台产物，或源码构建：Windows/Linux amd64 均为纯交叉编译产出）
#    拷贝即跑：零配置可启动，首次启动自动建库建表（无任何前置脚本）

# 2. 启动服务
./aiteam serve
#    配置探测基准=exe 所在目录（部署根），与执行命令时所在目录无关：显式 --config >
#    exe 同目录 aiteam-config.json > 内建默认；exe 同目录无配置文件时首跑自动生成一份
#    （内建默认值+_doc 说明，改后重启生效）。默认监听 0.0.0.0:8310，数据库默认落 exe
#    同目录 db/aiteam.db（db/ 自动创建）；显式指定：./aiteam serve --config <path>

# 3. 验证（本机探活，无鉴权）
curl http://127.0.0.1:8310/api/v1/ping
#    返回 {"data":{"version":"...","now":"..."}} 即服务就绪
```

服务进程以 Ctrl-C 优雅停机；进程被强杀后重启，已入库数据不丢（WAL 自恢复）。

**服务化部署（开机常驻）**：部署根=exe 所在目录——自启动器**只配可执行路径（AppPath）即可，无需设置工作目录**（config/db 自动落 exe 目录，无工作目录依赖）。Windows NSSM 一条命令：`nssm install aiteam "<exe 绝对路径>" serve`；sc 同理（`binPath=` 指向 exe 并带 `serve` 参数）；Linux/macOS systemd/launchd 完整配置与反注册见 README「服务自启」节。

> 开发调试提示：用 `go build -o aiteam ./cmd/aiteam` 构建后运行（或 `--config` 显式指路）；不要用 `go run` 起 serve——go run 的 exe 在 go-build 临时目录，config/db 会生成到那里（每次重建即全新空库）。

## ② 配置字段表

**服务端配置**（`aiteam-config.json`，与二进制（exe）同目录——即 serve 的探测基准，与执行 serve 时所在目录无关；可省略走全部默认值）：

一键生成配置样例（内建默认值+每段中文说明，改完重启 serve 生效；已存在不覆盖，`--force` 覆盖）：

```bash
./aiteam config init
```

```json
{
  "_doc": "aiteam 服务配置样例；全部字段可省略走默认值",
  "listen": "0.0.0.0:8310",
  "db": {"type": "sqlite", "path": "db/aiteam.db"},
  "auth": {"token_enabled": false, "token": ""},
  "session": {"heartbeat_timeout_sec": 900},
  "watch": {"poll_interval_sec": 5, "sentinel_timeout_sec": 15},
  "board": {"poll_interval_sec": 5},
  "timezone": "Local"
}
```

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `_doc` | string | — | 样例内注释字段，加载时忽略，可保留可删除 |
| `listen` | string | `0.0.0.0:8310` | HTTP 监听地址；修改后重启生效 |
| `db.type` | string | `sqlite` | 一期仅支持 `sqlite`，其他值启动报错 |
| `db.path` | string | `db/aiteam.db` | SQLite 数据库文件路径（相对值相对 exe 所在目录解析，绝对路径照用；`db/` 目录自动创建）；修改后重启生效 |
| `auth.token_enabled` | bool | `false` | token 鉴权总开关，默认关（内网直连零鉴权）；开启后 CLI 与看板同口径校验 |
| `auth.token` | string | `""` | token 凭证值；`token_enabled=true` 时必配 |
| `session.heartbeat_timeout_sec` | int | `900` | 会话失联阈值（秒，默认 15 分钟）；项目登记时可按项目覆盖 |
| `watch.poll_interval_sec` | int | `5` | watch 哨兵默认轮询间隔（秒） |
| `watch.sentinel_timeout_sec` | int | `15` | 哨兵失活阈值（秒，默认 3×轮询间隔）；失活仅为可见标记，不影响消息可得性 |
| `board.poll_interval_sec` | int | `5` | 看板主轮询间隔（秒） |
| `timezone` | string | `Local` | 时间窗判定时区基准（IANA 名如 `Asia/Shanghai`，或 `Local`=服务进程时区） |

**CLI 客户端配置**（`.aiteam/cli.json`，可选；放在执行 CLI 的工作目录，仓级可提交 git 全仓共享）：

```json
{
  "_doc": "CLI 连接配置（仓库级可提交共享）",
  "server": "http://<服务机>:8310",
  "token": ""
}
```

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `_doc` | string | — | 注释字段，加载时忽略 |
| `server` | string | 查找链末位默认 `http://127.0.0.1:8310` | 服务地址（查找链见④） |
| `token` | string | `""` | token 凭证（优先级 `--token` > `AITEAM_TOKEN` > 本字段，见③） |

注：配置在启动时加载——修改 `listen` / `db.path` 后需重启服务生效；token 开关与值变更后同样重启生效。`_doc` 字段服务端与 CLI 均忽略。

## ③ token 启用（可选）

默认关闭（内网直连零鉴权，无任何凭证可用全部命令与看板）。需要开启时：

```jsonc
// aiteam-config.json —— 改两处后重启服务
"auth": { "token_enabled": true, "token": "<足够长的随机串>" }
```

- **CLI 带 token**（优先级从高到低）：`--token <值>` 命令行参数 → `AITEAM_TOKEN` 环境变量 → `.aiteam/cli.json` 的 `token` 字段。无 token 调用被拒：非零退出（退出码 4），stderr 明确报鉴权错误。
- **看板带 token**：首次用 `http://<服务机>:8310/?token=<token>` 进入，页面记住凭证，之后无需再带；无 token 访问看板数据被拒。

## ④ CLI 接入

客户端与服务端是同一个二进制——把 `aiteam` 拷到各客户端机器（与服务端同版本）即可，无独立安装步骤。

**服务地址查找链**（从高到低，命中即止）：

1. `--server <addr>` 命令行参数
2. `AITEAM_SERVER` 环境变量
3. `./.aiteam/cli.json`（工作目录，仓级，可提交共享）
4. `~/.aiteam/cli.json`（用户级）
5. 默认 `http://127.0.0.1:8310`

注：这是客户端**连接**配置，不是会话状态——aiteam 会话身份零本地文件（见下），换机重开同名会话即同一实体。

**身份四参**（`--project` / `--column` / `--session` / `--role`，凡带会话语义的命令必填，缺漏=本地校验失败退出 2）：

| 参数 | 含义 | 约定 |
|------|------|------|
| `--project` | 项目 code（如 `proj-a`） | 先登记（⑤步骤） |
| `--column` | 栏目 code（如 `01`） | 项目内唯一，先登记 |
| `--session` | 会话名（如 `controller-A` / `executor-B`） | 同栏目内唯一；换机重开同名=同一会话，幂等 |
| `--role` | 角色名（如 `controller` / `executor`） | 命名规约三种形态：`controller` / `executor` / `executor_<标识>`（换班用裸值，多执行者用后缀区分）；其他值服务端拒收（400 `invalid_role`）；信箱与可见性按角色记账 |

每次 CLI 调用自动携带身份四参到服务端：首次调用自动注册会话并开始心跳，此后每次调用刷新心跳（无独立心跳命令）。超过失联阈值（见②）无任何 CLI 活动的会话在 status/看板标记失联。

**send 的镜像双写**：send 成功后 CLI 自动在**发送方项目 git 仓库**追加一行审计镜像（`<仓库根>/.aiteam/mirror-<项目code>-<栏目code>.md`，一行一条消息；git 跟踪但不自动 commit，随正常流程提交）。因此执行 CLI 时 cwd 应位于项目仓库根目录。

**跨项目定向（`--to-project <项目code>`）**：direct / chat 的目标可指向**同一服务实例**上登记的另一项目（如 proj-a 的会话发到 proj-b 的目标角色/会话；非跨服务器路由——目标项目须与发送方登记在同一服务端）。direct 落点栏目=目标项目中与发送方 `--column` 同 code 的栏目（CLI flag 面无 `--to-column`）。三要点：

- **组合约束**：`--to-project` 仅与 `--to-role` / `--to-session` 组合合法；与 `--bus` 同给=本地用法错误退 2 不发请求（bus 是发送方栏目广播，无目标项目域可锚）；值传空白串视同缺省（=项目内发送）。
- **错误分流**：目标缺失按层 404、CLI 均退 4——项目层 `project_not_found`（CLI 特判文案「目标项目不存在: <项目code>」）；栏目层 `column_not_found`（「栏目不存在: 项目 <项目code> 栏目 <栏目code>」）；会话层 `target_session_not_found`（「目标项目 <项目code> 无会话 <会话名>」）——错误信息均带目标项目 code，指明真实缺失层级。
- **token 前提**：token 是服务级开关（③，全实例单值、非按项目）——开态下跨项目调用与项目内同一道闸：必带该 token，无/错 token → 401 `auth_required`（退 4）。

## ⑤ 双客户端接入示例

场景：服务机已完成①，服务地址 `http://192.0.2.10:8310`（示例用文档保留段 IP，实际填你的服务机地址）。两个客户端=两种可在 bash 调命令行的 AI 会话工具（同机两个终端亦可）：

| | 客户端 A（总控） | 客户端 B（执行者） |
|---|---|---|
| cwd | 项目 git 仓库根（工作副本一） | 同一项目仓库的另一工作副本（机器二） |
| 会话 / 角色 | `controller-A` / `controller` | `executor-B` / `executor` |

**客户端 A（总控）——登记与首次发送**：

```bash
cd <你的项目仓库根>                # 镜像与 cli.json 均落在 ./.aiteam/
mkdir -p .aiteam
cat > .aiteam/cli.json <<'EOF'     # 仓级连接配置，可提交 git 共享
{ "server": "http://192.0.2.10:8310", "token": "" }
EOF
curl http://192.0.2.10:8310/api/v1/ping    # 连通验证（身份未就绪时勿用 project list——其身份四参必填）

# 空库首建（自举引导）：首条项目/栏目还没有任何已登记身份域可挂——CLI 必带身份
# 四头，走完整链会因项目不存在 404 死锁；服务端只对这两条登记端点豁免身份四头，
# 故用 curl 自举，再走 CLI（豁免=免身份四头，不免 token 鉴权——见下方 Bearer 头）。
# ⚠️ 自举 curl 不带 name（name 省略合法）——Windows 下 curl 命令行发中文 body 会
# 编码损坏入库乱码（看板显示乱码）；中文名建好后用 CLI update 补（CLI 路径编码正常）：
curl -X POST http://192.0.2.10:8310/api/v1/projects \
  -H "Content-Type: application/json" -H "Authorization: Bearer <token>" \
  -d '{"code":"proj-a"}'
curl -X POST http://192.0.2.10:8310/api/v1/projects/proj-a/columns \
  -H "Content-Type: application/json" -H "Authorization: Bearer <token>" \
  -d '{"code":"01"}'
# 补中文名（挂身份+幂等）：
aiteam project update --code proj-a --name "示例项目" …
aiteam column update --project proj-a --code 01 --name "示例栏目" …
# ↑ 两处 Bearer 头：token 未开启（③默认关）时可省；token 开启时必带，漏带同样
#   401 auth_required（登记端点豁免的只是身份四头）

# （可选）补审计留痕：上方 curl 自举未挂会话身份；用幂等 update 改同值即可把操作
# 挂到总控身份下（勿重放 register——同端点再登记会 409 project_exists 退 4）
aiteam project update --code proj-a --name "示例项目" \
  --project proj-a --column 01 --session controller-A --role controller
aiteam column update --code 01 --name "示例栏目" \
  --project proj-a --column 01 --session controller-A --role controller

# （可选）登记共享资源：端口/账号段/数据段先登记后使用，冲突即拒
aiteam resource register --project proj-a --column 01 --type port --value 8080 \
  --note "示例服务端口" --session controller-A --role controller

# 定向发送：目标=01 栏目 executor 角色（important=重要级）
aiteam send --project proj-a --column 01 --session controller-A --role controller \
  --to-role executor --level important --body "接入示例：请 poll 确认并回复"
# → OK seq=1 time=<服务端时间>；镜像文件 ./.aiteam/mirror-proj-a-01.md 自动新增一行

aiteam watch --project proj-a --column 01 --session controller-A --role controller &
# 后台哨兵：01/controller 信箱命中新消息即退出（退出码 0）唤醒会话；平时靠主动 poll 兜底
#（好记比喻：哨兵=传呼机，有人送信才响；--max-wait N=闹钟，到时也响一次〔退出码 6〕。
# 日常建议：纯传呼机+哨兵常挂。哨兵常挂（消费端适配前置）：干活中也挂——值守与工作
# 并行，不因开工而摘哨；挂法前提=命中有会反应的消费端（宿主后台任务退出通知/人在终端/--on-hit 钩子），
# 无消费端的分离式挂法（无人读的日志/nohup）=哑炮，禁用。响铃→poll→按 level 分级响应→立即重挂，
# 全时段秒级收信；--max-wait 仅作无消息事件场景的故障兜底。系统健康巡检见 scripts/watchdog.sh）
```

**客户端 B（执行者）——接收与回复（收发闭环）**：

```bash
cd <你的项目仓库根>                # 执行者侧工作副本根
mkdir -p .aiteam
cat > .aiteam/cli.json <<'EOF'     # 同一服务地址；也可随 git 共享拉下来
{ "server": "http://192.0.2.10:8310", "token": "" }
EOF

# 拉取信箱（身份四参=会话实体；首次调用自动注册 executor-B 并开始心跳）
aiteam poll --project proj-a --column 01 --session executor-B --role executor
# → [1] important <服务端时间> controller-A@01(controller) / 正文…

aiteam ack --project proj-a --column 01 --session executor-B --role executor
# 推进消费位点（幂等）；此后 poll 不再返回已确认消息

# 回复总控（定向到同栏目的 controller 角色）→ 定向收发闭环完成
aiteam send --project proj-a --column 01 --session executor-B --role executor \
  --to-role controller --body "executor-B 已接入，示例消息已处理"

aiteam watch --project proj-a --column 01 --session executor-B --role executor &
```

A 侧验证闭环：`aiteam poll ... --session controller-A --role controller` 拉到 B 的回复后 `aiteam ack ...` 收尾；再跑一次全局现场汇总确认两会话在线、待消费归零：

```bash
aiteam status --global --project proj-a --column 01 --session controller-A --role controller
# 一行式输出：各栏目 pending/位点/哨兵活性/时间窗 + 会话心跳面 + block 未回执清单
# （会话压缩/重开后恢复现场=同样只跑这一条）
```

要点：两侧 `--session`/`--role` 不同，信箱与对话流才相互独立；`block` 级消息接收方须 `ack --receipt <seq>` 逐条回执；三种目标形态=定向 `--to-role` / 总线 `--bus` / 会话对话 `--to-session`。

**poll/watch 防呆行为（role 错格自判）**：信箱按 role 分格、一格一人——`--role` 填错（如多执行者把 `executor_A` 填成 `executor`）时，定向消息仍投在正确的格，错格 poll 的定向面恒空。两条自判信号与一条动线：

**poll 跨格提示**：本格本次 poll 可见集内定向（direct）消息为 0、而同栏目他格有未消费定向时（只看定向面——对话流消息在不在不影响触发），stderr 逐格出一行提示；本格有定向消息时正常返回且不出提示（即使他格有积压）。逐字模板：

```text
提示：本格（role=<自己的role>）无定向消息；同栏目 role=executor_A 格有 3 条未消费定向——若你的身份应为该格，检查 --role 是否填错
```

多格时逐格一行；超过 5 格时服务端聚合为末行「提示：本格（role=…）无定向消息；同栏目另有 N 格共 M 条未消费定向——若你的身份应为其中一格，检查 --role 是否填错」。提示只进 stderr（stdout 渲染零改动，管道消费者不受扰）；`--json` 模式提示照出（面向人，机器可自解析响应中的 `cross_grid_hint` 字段——仅含目标 role 名与条数，零正文）。

**watch 命中行标注**：命中输出 `HIT seq=<n> level=<l> kind=<k> target=<t>`，target 按 kind 解读：`direct`→目标角色值（定向信投的格）；`chat`/`receipt`→会话对话流；`bus`→栏目广播仅总控。`--json` 模式 hits 元素带 `kind`/`target_role` 两键。

**错格自判动线**：哨兵响 + poll 本格无定向消息且出跨格提示 = 消息在别的格（chat 类消息按会话命中、不核 role——哨兵响不代表定向信在本格）：核对应挂格的 `--role`，改正后重试。

**watch 命中钩子（`--on-hit`）**：`--on-hit "<命令行>"` 让哨兵命中时**先照打 HIT 行**再执行钩子（AI 侧唤醒不被耽误），随后照常退出——一次性/重挂纪律零变化。钩子经 `sh -c`（unix）/`cmd /c`（windows）执行，**10s 超时强杀**；失败/超时仅 stderr 提示，**不改 watch 退出码**。命中数据经环境变量透出：`AITEAM_HITS_JSON`（全量命中 JSON 数组，含 `kind`/`target_role`）+`AITEAM_HIT_SEQ`/`AITEAM_HIT_LEVEL`（首条便捷键）；钩子自身输出走 watch 的 stderr（stdout 管道消费者不受扰）。**钩子=合格消费端**——分离式挂法配钩子即通知守护（人不在终端也能收推送）。

**per-OS 通知一行配方**（`--on-hit` 的命令行按值守链路平台就近取用）：

```bash
# Windows（响声，零依赖）：
aiteam watch … --on-hit "powershell -c [console]::beep(1000,500)"
# Windows（toast 通知，需一次性 Install-Module BurntToast）：
aiteam watch … --on-hit "powershell -c New-BurntToastNotification -Text 'aiteam 哨兵命中'"
# macOS（系统通知中心）：
aiteam watch … --on-hit "osascript -e 'display notification \"aiteam 哨兵命中\"'"
# Linux（桌面通知）：
aiteam watch … --on-hit "notify-send 'aiteam 哨兵命中'"
# 手机（ntfy 推送，任意平台可达）：
aiteam watch … --on-hit "curl -d 'aiteam 哨兵命中' -d tags=bell ntfy.sh/<你的主题>"
```

**`--force` 接管动线**：重挂 watch 遇「已有哨兵值班中（持有者=<会话名>，最后 ping Ns 前）——若为残留孤儿可 --force 接管」时——持有者是同事的活跃会话=**勿动**；确认是自己旧进程/已知孤儿（三类形态见⑩节）→ 加 `--force` 重挂：服务端同事务删旧锁插新锁，旧哨兵下次 poll 拿 `404 sentinel_not_found` 自然退出，一格一哨恢复单例。无占位时 `--force` =普通注册，无副作用。

**status 会话行命中留痕**：会话哨兵态后有值时缀「·命中Ns前」（最近一次哨兵命中距今）——「在挂≠在干活」的健康面，与看板徽标（「哨兵·N 分钟前命中」）同源。

## ⑥ 会话编制与子代理配置

**收发室比喻**：每个栏目的信箱按 role 分格、一格一人，定向消息按格投递。同格两人=抢信（消息被先 poll 的拿走）+吞信（对方以为送达，实际被截走）。换班=同一格换人：后到者用裸 `executor` 单值形态顶岗，服务端静默覆盖 role 并留审计。因此 role 只许三种写法——`controller` / `executor` / `executor_<标识>`（多执行者各占一格，如 `executor_A` / `executor_web-1`），其他值服务端拒收（`invalid_role`），完整规约表见 [README](../README.md)。类广播（面向全体）不走 role 目标，用 `--bus`。

多会话协作（总控 + 多执行者并行）的窗口开法与模型分档：

- **窗口开法与启动指令**：每个 AI 客户端会话窗口对应一个 aiteam 会话（总控一窗、执行者各一窗）。各窗口的启动指令（读什么、挂哨兵命令、并行纪律等全文）不要手写——init 已把模板渲染为项目根 `.aiteam/onboarding.md`（总控版 + 执行者 A/B/C 变体，更多执行者复制扩位）：开窗时把对应身份变体全文作为首条消息粘入该窗口即可；完整形态再读 `docs/planning/methodology.md`「一、方法论段」对应补全（两段连读=完整指令；模板源=`docs/planning/_template/onboarding.md`）。
- **cheap-model 子代理事先注册**：便宜档子代理需在所用客户端的**子代理注册处**事先配置（Claude Code 为项目 `.claude/agents/` 下的定义文件；其余客户端参照各自文档的 subagent/agent 自定义入口，同样是在项目或用户级配置目录落一个定义文件）。**注册表按会话启动加载——注册完成后需新开会话才可见**，请先注册再开工，避免中途重开会话。

**三档模型分配原则**（按判断密度花钱）：

| 档位 | 承担角色 | 承担工作 |
|------|---------|---------|
| 旗舰档 | 总控会话 | 决策、终审、调度——判断密度最高 |
| 标准档 | 文档子代理 | 方向性文档（PRD / 技术设计 / spec / plan） |
| 便宜档（cheap-model） | 机械产出子代理 | 规格已定的按章办事类产出：图绘制、帮助页成文、归档搬运、批量排查 |

- **降级口径**：客户端不支持多档子代理时，全部会话用同一档模型照常可跑——token 成本更高，但方法论（编制/指令模板/通讯纪律）不受破坏。
- **方法论执行技能**：编制依赖的 13 个方法论技能（Skill 实体）需先安装到所用客户端的技能目录，安装方式见⑪节。

## ⑧ backup 与恢复

```bash
# 热备：服务运行中可直接执行（SQLite VACUUM INTO，产出单文件一致性快照）
./aiteam backup --config aiteam-config.json --out ./aiteam-backup-20261002.db
# 无 --db/--config 时 backup 会读当前目录 aiteam-config.json（CWD 探测——backup 是
# 人跑的维护命令，保持 CWD 语义；注意 serve 以 exe 所在目录为基准，两者
# 探测域不同）。探测命中自定义 db.path 时输出行以 source=<路径>
# 明示实际源库。仍建议显式传 --config <路径> 或 --db <路径>：服务化部署（配置/库在
# exe 目录）从别处执行 backup 时 CWD 探测不到，必须指路；零配置部署可 cd 到 exe
# 目录直接省略参数（内建默认库 db/aiteam.db 相对 CWD 解析，与 serve 的落点重合）
# 不覆盖口径：目标文件已存在时报错退出（退出码 1），不覆盖旧备份——换文件名或先移走旧文件
```

恢复四步：

1. 停服务（Ctrl-C）；
2. 把备份文件复制为配置 `db.path` 指向的路径（默认 `db/aiteam.db`，相对 exe 所在目录），并删除同目录残留的 `aiteam.db-wal` / `aiteam.db-shm`；
3. 重启 `./aiteam serve`；
4. `curl http://127.0.0.1:8310/api/v1/ping` 验证就绪。

## ⑨ 故障语义表

**CLI 退出码（全命令统一）**：

| 码 | 语义 | 典型来源与处置 |
|----|------|---------------|
| 0 | 成功（watch=命中新消息） | 继续主流程 |
| 1 | 未知内部错误 | 客户端兜底/服务端 500；重试一次仍复现则呈报 |
| 2 | 参数/用法错误（本地校验） | 缺身份参/格式错；按 stderr 提示改命令 |
| 3 | 服务不可达 | 连接拒绝/超时；查服务进程与地址后重试 |
| 4 | 服务端拒绝 | 404/409/400/401 全部业务错（错误码+中文说明原样透传 stderr，如目标不存在/重复登记/资源冲突/鉴权失败） |
| 5 | 镜像写失败（消息已入库） | send 专属；按下方流程手工补镜像行 |
| 6 | watch 到期未命中（非错误） | `--max-wait` 到时；按需重新挂哨兵 |

**服务不可达口径**：任何 CLI 命令在服务不可达时统一 `ERROR: 服务不可达 <原因>（server=<addr>）` 输出到 stderr 并退出 3——无静默失败、无本地假状态（`rc>=3` 时脚本应呈报或重试）。

**退出码 5 的手工补镜像流程**（消息已入库，仅镜像行缺失）：

1. 读 stderr：CLI 会打印 `ERROR: 消息已入库 seq=<n> 但镜像写入失败: <原因>` 与 `手工补行: <完整行内容>` 两行；
2. 把「手工补行：」后的完整行内容原样追加到发送方仓库 `.aiteam/mirror-<项目code>-<栏目code>.md`（一行一条消息，行格式 `<seq> | <时间> | <级别> | <目标摘要> | <发送方> | <正文单行化>`）；
3. **不要重发 send**——消息已在服务端，重发=重复消息；补行动作幂等，人工确认无重复即可；
4. 补行后 `git status` 可见镜像修改，随项目正常提交流程入库。

## ⑩ 哨兵值守健康与排障

本节沉淀三起实战哨兵事故的教训，目标=零排障经验也能自诊断。词汇与全指南统一：孤儿持有者/`--force` 接管/消费端/命中留痕。

**正常值守长什么样**：看板会话行哨兵徽标「哨兵·N 分钟前命中」（最近一次命中时刻）+ CLI status 同源缀「·命中Ns前」。两信号口径：
- **留痕缺失**（无徽标/无缀）=哨兵没在挂或从没命中过——先确认哨兵进程在，再补挂；补挂前自查挂法前提=命中有会反应的消费端（哨兵常挂（消费端适配前置）纪律，见上方 watch 详解），否则命中了没人知道；
- **在挂但不命中**（进程在、该收的信没收到）=疑聋或错格——先跑 poll 看跨格提示（role 错格自判，见⑤节防呆段），再查消费端是否活着。

**孤儿持有者是什么与怎么产生**：信箱哨兵一格一哨（活进程持锁吃命中）。服务端只能判死（心跳 15s 阈值内自动接管），**活孤儿**（进程活着但已无人理会）服务端原理上无法自动识别——锁归属不可见，只能人判。三类实战形态：
1. **会话重启遗留**——旧会话窗关了，其后台哨兵进程还活着；
2. **Cron/循环拉起收班不清**——外壳脚本到点循环拉起哨兵，收班时没清进程（只许按自建 PID 精确清理，禁按映像名全局杀）；
3. **分离式挂法**——无人读的日志/nohup 挂法（纪律禁用：哑炮）。

**识别与处置三步**：
1. **看板健康面板**：该收信会话的哨兵徽标长期不动/缺失→疑孤儿或漏挂；
2. **200 持有者诊断**：直接重挂 watch（不带 --force），命中占位锁时输出「已有哨兵值班中（持有者=<会话名>，最后 ping Ns 前）——若为残留孤儿可 --force 接管」——持有者会话名+ping 年龄即判据：是同事在值=勿动，是自己旧进程/已知孤儿=下一步；
3. **`--force` 接管**：确认后加 `--force` 重挂，旧哨兵下次 poll 拿 `404 sentinel_not_found` 自然退出（详细动线见⑤节）。

**消费端挂法三形态与禁用项**：挂法前提=命中有会反应的消费端——
1. **宿主后台任务**：会话内 `&` 挂哨兵，宿主唤醒会话（AI 会话标准形态）；
2. **人在终端**：前台跑 watch，响铃即见；
3. **`--on-hit` 钩子**：分离式挂法配通知钩子=合格消费端（配方见⑤节）。
禁用=无消费端的分离式挂法（无人读的日志/nohup）——哑炮：命中了没人知道。

## ⑪ 方法论技能包安装

`internal/assets/skills/`（已 embed 进单二进制）是 S0~S7 流水线方法论的**执行技能包**（13 个方法论技能，SKILL.md 格式）：需求追问（requirement-grilling）、方案构思（brainstorming）、写计划（writing-plans）、子代理执行（subagent-driven-development）、spec 预审（spec-review）、TDD、系统化调试、完成前验证、code review 收发、worktree 隔离、分支收尾等。各契约与启动指令里「以 Skill 工具加载 XX」指的就是它们——纯 markdown 目录，需先安装到项目技能目录，Skill 工具才能发现并加载。

**安装（首选，init 默认）**：`aiteam init` 默认把技能包释放到项目 `.agents/skills/`——merge 语义：同名技能**保留你的现有版本**（绝不覆盖，适合已装过同源技能的项目），只新增缺失文件；汇总报告列出「新增 N，保留现有 M」计数，要换 aiteam 版=删该技能目录后重跑 init。`--no-skills` 显式跳过。

**安装（备选，手动链接到客户端技能目录）**：仓库自带幂等安装脚本（`scripts/` 下双平台各一），把仓内 `internal/assets/skills/` 逐技能链接到目标项目的 `.claude/skills/`（每技能一条链接；适合 clone 了本仓、想让 Claude Code 类客户端直接发现的形态）。源目录按脚本自身所在仓自动定位，与执行时所在目录无关；目标项目根缺省为当前工作目录。

Windows（PowerShell 5+，NTFS junction，免管理员权限）：

```powershell
cd <本仓克隆>/scripts
powershell -File setup-skills.ps1                    # 安装到当前项目根（当前工作目录）
powershell -File setup-skills.ps1 -Target <项目根>   # 安装到指定项目根
```

类 Unix / Git Bash（bash 调用；Git Bash 下自动改用 junction 兜底，因 MSYS 的 ln -s 会退化为拷贝）：

```bash
cd <本仓克隆>/scripts
bash setup-skills.sh                        # 安装到当前项目根（当前工作目录）
bash setup-skills.sh --target <项目根>      # 安装到指定项目根
```

**幂等语义**（重复跑零副作用；输出逐技能一行 `[安装]`/`[跳过]`/`[修复]`/`[报错]`，末尾汇总计数；源缺失或源下无任何技能=报错退出）：

| 目标现状 | 脚本行为 |
|----------|---------|
| 已是指向源的正确链接 | 跳过 |
| 链接存在但指向错 | 删旧建新（修复） |
| 同路径已是普通目录/文件 | 该技能报错（先备份再删除该目录后重跑），其余技能继续，退出码非零 |

**其他客户端**：zcode 等客户端把同样的 junction/symlink 建到其自己的技能目录即可（技能目录路径以各客户端文档为准）。SKILL.md 本质是 markdown 指令文件——**没有 Skill 工具的客户端可把技能内容当 prompt 模板手动粘贴使用**，方法论不绑定特定客户端。

## ⑫ 多机 git 协作拓扑

`aiteam init --topology` 提供两种协作口径：`single`（默认，单机 worktree 隔离）与 `distributed`（多机经共享远端仓协作）。无论哪种口径，init 都会把对应纪律节自动写进项目 `docs/dev-guide/base.md` 的拓扑区块（重跑 init 自动刷新该区块，其余产物零触碰）——**日常纪律以仓内 base.md 为准，本节只讲 distributed 形态的远端仓怎么搭**。

### bare 仓三步搭建（全新项目）

```bash
# 1. 建共享 bare 仓：任选一台机器或文件服务（自建形态；用托管平台则在平台建空仓，跳过本步）
git init --bare <仓>.git
#    产出纯仓库目录（本身不做开发），路径即下文 <url>

# 2. 各成员机器分别 clone（每人一个独立工作副本，各机各自分支开发）
git clone git@example.com:<仓>.git
cd <仓>
aiteam init --project <code> --name <名称> --topology distributed
#    项目发起人先跑 init 生成脚手架并随首个提交推入远端；其余成员 clone 已含脚手架，
#    补跑同参数 init 幂等零变更（增量幂等：产物已存在一律跳过）

# 3. 权限约定（谁可推主干）
#    个人分支（如 feat/<批次>-<任务>）：各自机器可推，push 频率=每任务收口即推
#      （测试绿+静态检查过就 push WIP 进度，防本机故障丢提交，跨任务囤积不 push 禁止）
#    主干分支（master）：仅合并序内当前合并者可推——按任务档既定行序串行，
#      自测全绿后 fetch 自查、merge --no-ff 回 master 并 push 更新远端主干；
#      不开人人直推主干（有托管平台时给 master 配保护分支机械落实）
```

> distributed 纪律细节（WIP push 频率 / fetch 前置自查 / 合并三步 / 合并序）由 `aiteam init --topology distributed` 写进项目 dev-guide，团队成员入仓先读它，本指南不重复维护。

### 既有仓接入远端

已在单机开发的仓升级到多机，不必重建：

```bash
git remote add origin <url>        # <url>=bare 仓路径或托管平台地址
git push -u origin master          # 首推主干
git push -u origin <各工作分支>     # 首推各在途分支，其余成员即可 clone 协作
```

### 单机 → 多机升级动线（四步，零停机零迁移）

1. **搭 bare 仓**：按上文三步搭建的第 1 步建共享仓（或托管平台建空仓）；
2. **接远端**：`git remote add origin <url>` + 首推 master 与各在途分支；
3. **重跑 init 换口径**：在项目根重跑 `aiteam init --project <code> --name <名称> --topology distributed`——init 增量幂等，**仅 dev-guide 拓扑节自动刷新为多机纪律，其余产物零变更**（planning 活文档等已存在一律跳过）；
4. **群发知会**：`aiteam send --bus --level important --body "项目已切换多机拓扑，git 纪律见 docs/dev-guide/base.md 拓扑节，各成员拉取最新纪律后再开工" --project <code> --column <栏目> --session <会话名> --role <角色>`——全体执行者会话经总线收到知会后再继续任务（身份四参=发送方会话身份，恒必填）。

### svn 团队说明

进度自动上报层（post-commit hook，init 在 git 仓根自动安装）仅覆盖 git——**aiteam 不做 svn 钩子**（svn 各服务端钩子环境差异大）。svn 团队的进度上报走手动层：各会话收口时手动执行上报命令，与自动层落库同表同效：

```bash
aiteam progress --batch <批次> --task <任务> --tests pass --summary "<一句话进度>" \
  --project <code> --column <栏目> --session <会话名> --role <角色>
# → OK progress=<id>；查看已收进度：aiteam progress list（同身份四参）
```

VCS 纪律口径本身 init 已有 `--vcs svn` 变体（契约与铁律文案按 svn 集中式适配），可与 `--topology` 任意组合。

## ⑬ init 产物分立四轴与版本升级动线

**产物分立四轴**（写入语义各不相同，动任何一边前先分清归谁管）：

- **AGENTS.md / CLAUDE.md 的 aiteam 区块**（`aiteam:begin`~`aiteam:end` 标记区间）=恒定一句话开工引导（开工第一读=读 `.aiteam/onboarding.md`），**不随 aiteam 版本变**；区块外你的内容零触碰。
- **`.aiteam/`（工具自管面）**：`onboarding.md`（启动指令·通讯域全集=通讯接入）+ `cli.json`（服务连接配置）+ send 镜像审计行——init 播种；`onboarding.md` 标记区间内属 aiteam 管理面勿手改（升级删除重播种会以模板覆盖）。
- **`docs/planning/`（项目活文档）**：渲染件 11——项目级 6：红绿灯 `project-status.md` / 执行者契约 `executor-contract.md` / 方法论段 `methodology.md` / 术语表 `CONTEXT.md` / 维护清单 `maintenance.md` / `s0-s7-stages.md`（S0~S7 阶段模板）+首迭代骨架 5：`iterations/v0.1/` 四件（立项档 `charter.md` / `PRD.md` / 技术设计 `tech-design.md` / 任务档 `development-task.md`）+spec 登记簿 `specs/INDEX.md`——项目自己滚动维护，init 只播种不覆盖（已存在一律跳过），升级永不触碰。
- **`docs/planning/_template/`（模板演进件源）**：方法论文档包 21 件原样播种（占位符不渲染，供复制取用）——**完整一套**：init 播种 `_template/` 后 spec/plan/adr/charter 等模板随项目可得，新迭代立项、功能级设计文档直接取模板复制。

**新迭代立项**（手工动作）：首迭代 `v0.1/` 骨架由 init 代劳；之后新迭代立项=从 `_template/` 复制四件（charter/PRD/tech-design/development-task）进 `docs/planning/iterations/vN/`，spec 落该迭代 `specs/` 并登记入 `INDEX.md`（登记簿取 `_template/index-template.md`）。

**模板升级提示**：模板骨架稳定，默认不升级（init 幂等跳过已有模板件）；如需新版模板=手动删除 `_template/` 后重跑 init。

**版本升级动线**（升级 aiteam 后重跑 init）：

- comm-only 形态：手动删除 `.aiteam/onboarding.md` 后重跑 `aiteam init --comm-only` 重新播种（不删则 init 跳过不覆盖，旧版继续在用；`cli.json` 与镜像审计行不动）。
- 完整形态：同法删 `.aiteam/onboarding.md`（与 `docs/planning/methodology.md`）后重跑 init；其余 planning 活文档一律不动，升级单个模板=手动删除该文件后重跑 init。
- 旧版中文名产物（如 `.aiteam/启动指令.md`）：init 播种新名后检测到会提示「确认新版在位后可手动删除旧文件」，init 不自动删除。
