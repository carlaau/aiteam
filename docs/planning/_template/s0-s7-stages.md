## S0 立项与需求冻结

<!-- 参照：立项档+需求澄清文档。S0 做不好=全线返工，冻结前的追问投入是全流水线性价比最高的一段时间。 -->

### 目标

把「为什么做/做什么/不做什么/谁来做/怎么算做成」冻结为一页立项档+一份需求澄清文档，形成 S1~S7 一切下游文档的唯一范围基线（上游冻结，下游只引用不增减）。

### 进出条件

- **进**：原始诉求在手（痛点有实证：事故计数/复盘记录/频率代价），独立仓库目录已就绪（git init）。
- **出**：立项档七节全且 §7 检查清单全勾；需求澄清分支全裁定+方案骨架+边界场景+YAGNI 清单齐；量化验收条目（可脚本化）定案；冻结基线入仓并登记进红绿灯禁改项。

### 产物清单

1. 立项档（`docs/planning/charter.md`，按 [charter.md](charter.md) 模板）。
2. 需求澄清文档（冻结基线：分支穷举裁定记录+术语表+方案骨架）。

### 动作要领

- 追问式澄清（requirement-grilling）：新功能域逐分支穷举，每问附推荐答案；事实自查、决策问人，产出落盘进 specs/ 目录。
- YAGNI 防加戏：「不做」与「做」同等重要，每条不做附半句理由；冻结后出现加戏=范围违规。
- 验收条目必须可脚本化（计数=0/时延上限/命令恢复现场），写不出判据的不配当验收标准。
- 立项确认与自治等级经用户批准后记入决策账本，冻结基线变更只能走决策账本翻账。

## S4 批次开发（重点：四循环滚动）

<!-- 参照：development-task.md §4 批次表+执行者契约。S4=四循环并行的机器：spec/plan 连产喂执行者，执行者 TDD 产出，合并序号制保 git 串行，审循环把关。 -->

### 目标

按批次表把全部 FR 逐批开发合并回 master：spec/plan 弹药不断供、执行者 TDD 满载、git 写全局串行、每批过审关批。

### 进出条件

- **进**：技术设计冻结+S4 编排定案（批次表落任务档 §4，行序=合并序号）；执行者窗口由用户开窗贴 [onboarding.md](onboarding.md)（一次性物理操作，开窗≠开工）。
- **出**：批次表全部行「已关批」；全量测试绿；dev 临时分支/worktree 清理净；检查点回写至最后一批。

### 产物清单

1. specs/ 下各批 spec+同名 plan（总控侧文档子代理产出）。
2. 各批代码/文档产物（执行者会话内子代理 TDD 产出，feat/ 分支合并回 master）。
3. 任务档 §4 批次表与 §6 检查点持续回写（状态机：已批→开发中→已合并待审→已关批）。

### 动作要领（四循环）

#### 循环一：spec/plan 提前连产（总控侧）

- spec/plan 恒由 {{CONTROLLER_SESSION}} spawn 文档子代理产出、总控预审代批——**执行者禁产 spec/plan**（读已批件开工）；总控主会话禁机械产出，只做调度/预审/终判。
- 提前连产滚动供弹：先行批依赖冻结设计即可产（不等前置代码批），保持执行者永远有已批弹药可领。
- spec 八节齐（范围/技术落点/任务边界/测试策略/结构影响评估/旧链清退盘点/往返账预估/待裁点）；plan 与 spec 同名配对，执行模式行字面保留（与派工指令三方一致）；待裁点带推荐口径供总控照推荐或改裁。

#### 循环二：TDD 子代理执行（执行者侧，五步纪律链）

每批必走全五步、顺序不可跳（技能名与随仓 skills/ 逐字一致，替换即断链）：

1. **using-git-worktrees**——收开工令后建 worktree+`feat/{{BRANCH_PREFIX}}<N>` 分支（隔离开发；状态/信号回写一律操作主仓路径）。
2. **subagent-driven-development + test-driven-development**——plan 每个实现任务 spawn 独立子代理，子代理内测试先行（红→绿→重构）；主会话只做任务下发/结果审查/commit 收口，**主会话禁止直接写实现代码与测试**（实现类任务必须子代理；封闭例外：交互式浏览器调试/用户在环/git 合并高危操作/哨兵与信号回写）。
3. **requesting-code-review**——合并前自审一轮：对照 plan 任务清单/AC/工程规范逐项过，问题当场修复（修复属自测的一部分）。
4. **（含 Web 页面的批次）浏览器自测**——GUI 黑盒点走查核心动线，修完复测；纯后端/文档批在 plan 执行模式行声明跳过。
5. **finishing-a-development-branch**——全过才收尾：回主仓走合并三步（见循环三）。

#### 循环三：合并（行序=合并序号制）

- **行序=合并序号**：批次表行序即合并顺序。执行者自测过后，**见自己行以上全部「已合并」**才自行走合并三步：①rebase 最新 master（冲突由合并者解决）→ ②全量重跑（全部测试+静态检查零报错，不只跑本批）→ ③`merge --no-ff` 回 master。
- **远端操作（push/建远端）按 {{REMOTE_POLICY}}**；git 写全局串行由合并序号制保证，不靠约定靠状态面。
- 并行期零全局产物变更（共享 schema/全局配置首批一次建齐）；spec 发现需要全局变更立即回报总控排全局变更窗，不许私改。
- 合并后批次表置「已合并待审」+用 `{{PROJECT_BIN}} send` 向总控发信号（aiteam CLI 语境）。

#### 循环四：审循环（总控侧）

- 初审：总控对「已合并待审」批次按 spec §一 AC 口径逐条对账（初审子代理可并行 spawn）；**初审通过必落盘**（批次表留痕），不靠记忆。
- 终审：设计复核+跨批一致性；终审与后续开发重叠（「已合并未终审」=设计内状态，排队不阻塞）。
- 代批留痕：spec 批准/待裁点改裁/编排修订逐笔记任务档 §5 决策账本（append-only，可翻账推翻，推翻=返工批次）。
- 关批：终审过+证据齐才置「已关批」；返工单优先派机动返工位执行者直接在 master 追加修复 commit，不占主链合并序号位。
- 时间盒：单批 ≤{{TIMEBOX_HOURS}} 小时会话时间，到点收尾写状态停下汇报，不无限磨。

## S5 验收脚本化

> **【规划态】以下按任务档 §8 量化验收条目+PRD §4 产品验收的既定口径写骨架——以你项目 S5 实况回填校正**

<!-- S5 = 把「解决了没有」从主观判断变机械结论：全部量化验收脚本化，跑一遍出 PASS/FAIL。 -->

### 目标

产品级验收全部脚本化：PRD §4 的 V 系列验收逐条实现为可执行脚本，全部 PASS+AC 抽验通过=「解决了」的机械证据。

### 进出条件

- **进**：S4 批次表全部关批（全链路就绪）；PRD §4 验收 V 清单与观察窗已冻结。
- **出**：验收脚本族入仓且全 PASS（含负样本自测：必命中用例命中、零命中用例退出 0）；结果记入检查点与红绿灯。

### 产物清单

1. 验收脚本族（一 V 一脚本或一脚本多子项，零外部依赖）。
2. 验收运行记录（PASS 判据逐条对拍输出留档）。

### 动作要领

- 脚本形态照 PRD §4 表逐条实现，不改判据——实现中发现判据不可达，回 PRD 走决策账本改判，不许脚本迁就实现。
- 脚本自身断言先行（先写命中/零命中判据用例再实现），与 TDD 同纪律。
- 观察窗口径（在哪段时间/哪个范围统计）写死在脚本头部注释，防事后挪窗。

## S7 发布与脱敏终审

> **【规划态】本节为骨架口径——以你项目 S7 实况回填校正**

<!-- S7 = 外发不可逆的最后闸门：脱敏终审是用户硬触点，公开远端在终审通过后才创建。 -->

### 目标

通过用户亲自脱敏终审后发布：清理开发期痕迹、squash 单 initial commit、建公开远端首发。

### 进出条件

- **进**：S6 复盘收口；全仓脱敏自查脚本零命中（工作区）。
- **出**：用户终审通过（硬触点，{{FINAL_REVIEW_ITEM}}，外发不可逆不可代批）；公开远端创建+首发版本打标；发布物料（README/LICENSE/接入文档/帮助文档）终版齐。

### 产物清单

1. squash 后的公开仓（单 initial commit，开发史不入公开历史）。
2. 终审记录（终审项清单逐项勾+用户确认留痕）。

### 动作要领

- **脱敏终审硬触点**：git 历史 blob 级清查+全仓机械扫描双保险——开发期私有信息一旦进过历史，唯一兜底=squash 重写为单 initial commit 后再公开；终审由用户亲自过项，AI 不得代批。
- **squash 单 initial commit**：发布前把全部开发期 commit 压为单个 initial commit（同时物理清退开发期过渡脚本与信箱目录）。
- **建远端时机**：公开远端在终审通过后才创建；此前本地开发禁 push 禁建远端（红绿灯禁动作全程在位）。
