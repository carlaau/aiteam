## 第一章 角色契约

### 1.1 四角色定义与职责边界

| 角色 | 形态 | 一句话定义 |
|---|---|---|
| **总控** | 常驻会话（用户主窗口） | 规划+调度+审查+对用户唯一接口+文档子代理池，S0~S7 全程 owner；**只做决策与审查，机械产出为零**。调度=**信号驱动+空闲巡检双机制**：每次被唤醒处置完信号，顺带盘点全体执行者负载——空闲立即找活派（空闲是静默态不产生信号，巡检是发现空闲的唯一手段，实战教训：机动位空闲 4 小时无人察觉）。**活性判定以心跳数据为准**（`status`/哨兵活性端点），进程探测为单证据禁判死 |
| **文档子代理** | 总控会话内 spawn，无需独立开窗 | 判断型文档工厂（立项档/PRD/技术设计/spec/plan/领域文档/ADR 三道门判定）+ 代码**初审**（AC〔验收标准〕逐条对账）；不写代码、不改代码、不直接对用户承诺范围 |
| **执行者** | 独立窗口（用户开窗贴启动指令） | 产出工厂（代码+测试+机械产出）；worktree+feature 分支，按已批 spec/plan TDD 开发 |
| **cheap-model 子代理** | 总控/执行者 spawn（客户端子代理注册处配便宜档） | **规格已定的一切机械产出**：图绘制（吃判断侧出的规格）/帮助页成文/归档搬运/批量排查粗活 |

### 1.2 禁做清单（按角色）

**总控**：
- 只做三类事——**写文档**（含 spawn 文档子代理）、**审查**（读代码/证据/diff 后判断，只读不出手）、**调度**（批次状态/派工/对用户汇报）。除写文档外一切执行类不做：不写代码、不跑测试、不浏览器操作、不构建部署、不动数据（主会话直干封闭例外见 1.3，例外优先于本条字面禁令）。
- 「核对/复验/复核」在本档一律指审查性质（只读判断）；发现问题只能派单（返工清单），不能自己上手修。
- 禁机械产出（第五章 5.2）；spec/plan 长文起草恒派文档子代理，总控只终判定稿。

**文档子代理**：
- 不写实现代码；不越任务书范围自由发挥；不直接对用户承诺范围（对用户出口只有总控）。

**执行者**：
- **禁止产 spec/plan**（恒由总控侧文档子代理产出）；读已批 spec/plan 开工，不自由发挥超出 plan 范围。
- **开窗≠开工**：开工唯一定义=收到开工令信号（前置=该批 spec 已批）；待命期无信号属正常（待命≠停滞），禁止无信号自行开工。
- 不碰他人批次产物；测试自造自清、只清自己标识域。

**cheap-model 子代理**：
- 只干规格已定的机械粗活；规格未定（需要判断决策）的活升档给判断侧，不自行拍板。

> **启动指令两要素原则**：执行者启动指令只含「你是谁+听哪」（身份+哨兵挂法），任务与槽位**不写进指令**——干什么=派工信号携带指针（批次表行/spec 路径），用什么=开工时自助读任务档槽位表。指令只管身份，信箱管任务。

### 1.3 实现类任务必须子代理（主会话封闭例外）

总控与执行者的主会话都是**长窗口**（一个窗口连跑多个批次），必须保持「调度器+终判」角色。**执行类工作（写码/写测试/跑构建改产物/文档草稿/文件审读）必须 spawn 子代理执行，主会话禁止直接动手**——上下文隔离是流水线能连跑的前提，不是效率偏好：主会话直干一个大批次即吃掉大半上下文，后续批次空间耗尽、中途溢出=现场全丢；子代理任务自包含、可重试、用完即弃。

| 活 | 委托方式 |
|---|---|
| 文档起草（spec/plan/报告） | 子代理读输入产草稿 → 主会话终判定稿 |
| 文件审读（审 diff/审 spec/对账 AC） | 子代理（可并行多个：查事实引用/查规范合规/对账 AC）→ 汇总后主会话终判 |
| 批量机械活（迁移核对/死代码扫描/文档同步） | 子代理（cheap-model） |
| **代码实现（执行者窗口）** | **每个实现任务 spawn 独立子代理（测试先写：红→绿→重构）** |

**主会话直干例外（封闭清单，不得扩大解释）**：① 交互式浏览器调试/联调 ② 需用户实时在环的操作 ③ git 合并/push/建删分支等高危单发 git 写操作 ④ 状态/信号回写。

### 1.4 通讯纪律（aiteam CLI 语境）

- **总线=aiteam 服务**：会话间不直接通信，一切跨会话信号走 `aiteam send`（服务端 SQLite 原子写+递增序号，重号机制性消灭）；发送成功后 CLI 自动双写审计镜像到发送端仓库（`.aiteam/mirror-*.md`），随项目 git 留痕。**用户触点由 2.2/2.3 按自治等级定义，日常流转零传话。**
- **「信箱」语义**：每会话按「栏目+角色」拥有一只逻辑信箱（column+role 定向地址），另有总线（`--bus` 全员可见）与会话对话（`--to-session`）两种投递形态。
- **role 命名规约（一格一人）**：`controller` 单值（主控独格）或 `executor_<标识>`（下划线分隔，一人一格）——**多人共填同值 role=共用信箱=抢信+吞信**（一个 ack 位点，先取者推进后者永不可见）；服务端拦投递（`agent_conflict`）+前缀校验（`invalid_role`）；类广播用 `--bus`，会话粒度对话用 `--to-session`，看板用户自成体系不占 role。

| 命令 | 用途 |
|---|---|
| `aiteam send` | 发信号。定向（`--to-role` 对方角色）；`--level normal\|important\|block` 分级，**block 阻断级需对方 `ack --receipt` 逐条回执** |
| `aiteam poll` | 拉取自己信箱未消费消息（幂等：未 ack 前重复 poll 返回同批） |
| `aiteam ack` | 处置完推进消费位点（服务端记账）；block 消息回执 |
| `aiteam status` | **恢复现场单命令**：待消费数/位点/哨兵活性/当前允许阶段/阻断未回执清单（单栏目或 `--global` 一行式） |
| `aiteam watch` | **会话内后台哨兵**（`aiteam watch ... &`）：轮询自己信箱，位点之后有新消息即输出摘要退出 0，借「后台任务退出 re-invoke 会话」机制加速唤醒；`--max-wait` 到时退出 6（非错误） |

- **两步落盘（缺一=断链）**：状态/结论写**任务档**（上下文载体），信号走 **`aiteam send`**（唤醒载体）——只写任务档不发信号，对方哨兵听不见。
- **位点记账**：poll → 处置 → `ack` 推进；位点由服务端持久记账，重复 ack 幂等无副作用。
- **哨兵=watch+主动轮询双机制**：watch 加速唤醒；poll 兜底保证消息可得性（哨兵被杀不影响收信）。**任何不确定时刻（会话压缩恢复/重开窗/哨兵疑似死亡）第一动作=跑 `aiteam status`，禁止凭记忆重挂或开工。**
- **醒来第一读**：被唤醒后先 poll 未消费消息 → 按指针读任务档对应节 → 干活，不凭记忆开工。
- **共享文件提交机械闸（闸位必须前置）**：任务档/决策账本等 planning 类共享 md 多方共写——**append 前独立一步 `git status` 该文件：非空（他人未提交行挂工作区）=停手等对方 commit 后再写**；核对与 append/add/commit **永不写进同一复合命令链**（闸在复合链内=看到输出时已提交，放在可回退动作之后=不闸——实战五例的终局教训）；commit 前 `git diff --cached` 新增行数必须恰等于自己本次编辑行数，不等即 reset 停手；追加写入首字符必须是换行（无尾换行的文件直接 `>>` 会黏连成巨行）。
- **挂起任务解锁=等总控续作令**：等依赖合并的挂起任务，合并不由自己发现——上游合并的完成信号必达总控，总控按批次表行序 `send` 续作令（哨兵命中即醒），见令即 rebase 续作。（历史注：文件管理时代的「禁等知会+闹钟自查」纪律源于知会通道不可靠、哨兵一次性断链；aiteam 消息必达+哨兵常挂后该约束解除，依赖调度收归总控——执行者不自查依赖、不带闹钟。）
- **待命=纯传呼机值守（哨兵常挂）**：哨兵不带 `--max-wait`（默认无限等）——有人送信才响（退出码 0），无信永不唤醒（好记比喻：传呼机，没有闹钟）。**哨兵常挂（消费端适配前置）**：干活中也挂——值守与工作并行，不因开工而摘哨；**挂法前提=命中有会反应的消费端**（宿主后台任务退出通知/人在终端/--on-hit 钩子），无消费端的分离式挂法（无人读的日志/nohup）=哑炮，禁用；响铃→poll 读信→按 level 分级响应（block=立即停手 / important=当前原子步骤完成后处理 / normal=本轮干完统一处理）→**立即重挂**（哨兵一次性，命中即消耗，忘挂即聋）。
- **值守哲学（闹钟=兜底件，不是调度器）**：流转纯事件驱动，健康系统日常不需要任何闹钟参与调度——若团队流转要靠 `--max-wait` 定时唤醒推动，说明消息链有断点（哨兵孤儿/信号漏发），**修系统，不是调闹钟**。`--max-wait` 仅用于无消息事件可用的临时自查场景（故障兜底件）。系统健康巡检归总控侧 `scripts/watchdog.sh`（进程级脚本：服务可达性+会话心跳，不唤醒会话，异常经消息链报告 controller，人在回路）；**哨兵必须绑定活会话宿主，否则只有值守无通知**（会话压缩/重开后旧哨兵孤儿化=进程活但通知通道死，且幂等锁拦截新哨兵——处置=核对锁主可追溯性，孤儿即杀即清锁重挂；让位前先核对锁主身份，幂等退出≠一定有人在正确值守）。

### 1.5 全局铁律速查

1. **spec/plan 恒由总控侧文档子代理产出；执行者禁止产 spec/plan**——读已批件开工。
2. **开窗≠开工**：开工唯一定义=收到开工令信号（前置=该批 spec 已批）。
3. **实现类任务必须子代理**（例外仅 1.3 封闭清单）。
4. **自测过即合并**（审查后置，合并不需用户确认）；**「初审通过」必单独落盘禁跳步**（3.5）。
5. **两步落盘**：状态写任务档+信号走 `aiteam send`；**git 写操作全局串行**（3.4）。
6. **总控只做写文档/审查/调度三类事**，机械产出为零。

## 第二章 S0~S7 总览

### 2.1 七阶段调度视角一览

> 各阶段目标/进出条件/产物清单/动作要领的详细模板见 [S0~S7 阶段模板](./s0-s7-stages.md)；「谁批」列的实际形态按 2.3 自治等级落。

| 阶段 | 目标 | 关键产物 | 出口审批 | 执行形态 |
|---|---|---|---|---|
| S0 规划基线 | 边界/依赖确认+需求冻结入仓 | 立项材料/冻结需求基线 | 用户确认 或 总控代批+账本 | 单会话（总控） |
| S1 工程规范 | 开发规范通用化入仓 | dev-guide 规范文档 | 同上 | 单会话（总控，长文派文档子代理） |
| S2 PRD | 功能清单冻结（FR〔功能需求〕+AC 全编号） | PRD | PRD 冻结批 | 文档子代理起草+总控终判 |
| S3 技术设计 | 结构设计冻结（架构/表/API/图） | 技术设计文档 | 两级审批链（预审+终批） | 同上 |
| S4 批次开发 | 按批次产出代码+测试 | 批次表/spec/plan/代码/批次状态 | 审循环（第三章） | 总控+执行者流水线 |
| S5 测试与验收证据 | AC→TC〔测试用例〕全量化+证据回填 | TC 批次表+证据（文件:行号/测试输出/实测响应） | 总控审证据（只读） | 执行者跑测回填 |
| S6 业务验收 | 用户主场走查 | DoD-AC 走查清单+走查结论 | **用户亲自**（任何自治等级不代批） | 人工节奏，无哨兵 |
| S7 归档与收口 | 判断型/机械型资产回写+发布 | 领域文档/ADR/流程图/发布件 | 总控复核+用户抽查/终审 | 子代理两分派工 |

> S5~S7 补充纪律（S7 内容纪律详见第七章）：S5 无新 spec 批节点（TC 源自已批 AC；要改 AC=PRD 变更级回 2.2 重大档）；S6 缺陷=返工批次（master 追加修复+复走查）；S7 派工两分——判断性内容（ADR 提炼/领域文档框架/归档口径分析）→文档子代理，机械执行（图绘制/成文/搬运）→cheap-model；流程图=必备归档件不允许豁免。

### 2.2 代批分级三档（「只有重大决策才停下找用户」的授权边界）

| 级别 | 事项 | 处理 |
|---|---|---|
| **重大（必停等用户）** | AC/范围增减（PRD 变更级）；架构级分歧仲裁；动存量数据/资金/删除类操作；S6 业务验收；跨栏目边界；对外发布等不可逆动作 | 总控停下报用户，流水线等待 |
| **中（总控代批+事后留痕）** | spec/plan 质量问题打回返工；批次粒度调整（AC 不变）；非 AC 级实现取舍；初审/终审结论；spec/plan 待裁点裁定 | 总控按规则处理，**决策账本留痕**（日期+事项+裁定+依据，逐条入任务档决策账本节；用户可翻账推翻，推翻=返工批次） |
| **小（全自动）** | 文档格式与状态回写；审查排程；返工修复的验证；哨兵重挂 | 规则内自由执行 |

> 留痕形态实例：aiteam 开发任务档 §5 决策账本——PRD 冻结/技术设计冻结/全部批次 spec 代批/编排修订均逐条入账，即「中档代批留痕」的活样例。

### 2.3 自治等级三档（项目启动前一次性选定，写进项目红绿灯〔项目状态速览档，列当前允许/禁止动作〕头部）

| 等级 | 语义 | 用户触点 |
|---|---|---|
| **manual（开源默认）** | 标准人工审批：S0~S3 各冻结批、S4 每批 spec 批、S6 走查全部真停等用户批 | 每个审批节点 |
| **semi（半自动）** | 关键档用户批（如 PRD 冻结/S6 验收），其余（批次 spec/待裁点/编排修订）总控代批+账本留痕 | 关键节点 |
| **full-auto（全自动）** | 全部审批总控代批+决策账本留痕，仅保留 **3 硬触点**：① **启动确认**（立项时）② **最终验收体验**（部署真跑+量化验收）③ **外发前终审**（对外发布/脱敏审查类不可逆动作，必用户亲自） | 仅 3 硬触点 |

> **aiteam 自身即 full-auto 首例**（引注，通用流程描述）：其开发全程 PRD/技术设计/全部批次 spec 由总控预审代批+决策账本留痕，用户仅触点①②③；「技术信号类用户传话 0 次」写入其量化验收项。选 full-auto 的前提=2.2 中档留痕机制可信+用户接受「翻账推翻制」；流水线机制本身三档通用，切换自治等级不改流程只改审批节点落点。

## 第三章 S4 批次编排与审循环

### 3.1 批次切分（三层拆分权+粒度四依据）

| 层 | 内容 | 谁定 | 时机 |
|---|---|---|---|
| L1 功能清单（FR+AC） | 有哪些功能 | 总控定义，按自治等级批（2.3） | S2 随 PRD 冻结 |
| L2 批次（FR 打包/执行顺序/spec 份数） | 批次表 | **总控**编排（中档留痕报备；涉 AC 增减升重大档） | S4 开工前，写入任务档批次表 |
| L3 批次内文档结构 | spec 章节/plan 任务切分 | **文档子代理**自主 | 写文档时（裂变报备不审批，登记强制） |

**粒度四依据**：① **变更面聚类**（同表同页一批，防跨批文件冲突）② **依赖顺序** ③ **审查单元可消化**（一份 spec=一个完整能力；一次审查 diff 数百~两千行内）④ **风险隔离**。经验值：**一批=1~3 FR=1 spec+1 plan=执行者一个分支周期**。

**首批=全局基座批（串行）**：范围=建表 DDL→数据层骨架→全栈骨架→共享种子数据收口——用「收口」消灭并行期全局写冲突源。**审=表设计终审强度（唯一重审点）**：列完备性/索引/枚举值全集/生成器配置预判；基座漏项=并行中期全局写=全员暂停排队，宁可首批多花时间。此后并行期原则上零全局产物变更（见 4.3）；多执行者窗口刚性强时可再拆契约批先行（见 3.6）。

### 3.2 依赖判定三步法（判批次独立性，禁粗粒度采信编排时的依赖标注）

1. **列产物**：逐批列出本批消费的产物——依赖的包/页面底盘/测试输入数据。
2. **标归属**：每个产物标注归属（基座批全局产物 / 前序业务批深化产物 / 种子数据 / 自造测试数据）。
3. **判独立**：消费的**全是基座产物+种子+自造数据** → 批间独立可并行；消费前序业务批的**深化产物**（如必须调前批新写的业务方法/等前批页面才能自测）→ 真依赖，该对串行。

- **数据依赖不构成串行理由**：运行时数据=种子（基座批铺）或测试自造（数据正交自足）；「B 批的业务数据来自 A 批的页面操作」是伪依赖——测试可直接用种子+骨架 API 造态。
- **工程基座维度**（aiteam 实战教训）：逻辑零依赖≠工程零依赖——工程骨架未合并（go.mod 类构建清单/脚手架缺失）时测试根本无法编译，先行批照旧空转。列产物时除逻辑依赖外同步核**工程基座依赖**（依赖的构建文件/骨架代码是否已合并可得）。
- 有独立基座批的编排**必须按三步法重判**，不得沿用「依赖链→串行」粗规则。（aiteam 实例：两批经重判从串行改并行，实现四批同开满载。）

### 3.3 执行者模式决策表（呈用户拍板或代批入账）

| 决策要素 | 偏串行 | 偏并行 |
|---|---|---|
| 批次数 | ≤3 批 | ≥4 批 |
| 批次独立性 | 强依赖链（消费前序业务批深化产物） | 相互独立（三步法判定） |
| 交付压力 | 时间充裕 | 墙钟时间紧 |
| 审查密度 | 资金/算法敏感（终审吞吐吃满） | CRUD/页面密集 |

推荐规则：**满足「≥4 批且三步法判定大体独立」即推荐 2 执行者并行，否则串行单执行者**。2 个是甜点位，3 个是常设上限，4 个属短波满载形态（多执行者共用同一集成环境，隔离靠 4.2 槽位正交）。决策结果记任务档检查点。

### 3.4 合并序号制（git 写全局串行的并行解法）

- 批次表**行序=合并序号**，owner 列标执行者（见表即知序）。
- 执行者自测过后，**见自己行以上全部「已合并」**才**自行**走**合并三步**（免等总控在线发令，git 写串行由序号保证）：
  1. **rebase 新 master**（rebase 冲突由后合并者解决）；
  2. **全量重跑**测试（各自自测绿跑在对方未合并的旧基线上，rebase 后必须重验）；
  3. **`merge --no-ff` 回 master**。
- master 上短暂存在「已合并未终审」代码是**设计内状态**（换取执行者不被阻塞）；总控审循环与下一批开发天然重叠=隐藏红利。
- **流水线并行**：执行者执行批次 N 期间，文档子代理可并行写批次 N+1 的 spec/plan——前提是 N+1 不依赖 N 的代码（只依赖已冻结 PRD+技术设计的可提前写；须等前批代码才能写或自测的不可抢）。提前引用未来批次产物处一律标注「预期态（依据某批 spec §X），合并后开工前校对」，禁止写成既存事实。

### 3.5 批次状态机、关批与审循环

> **派工引用纪律**：总控派工令/依赖前提引用裁定点时**必回 spec 原文核对**——plan 可能滞后于 spec 裁定（plan-spec 断差实战：plan 写 3×interval 而 spec 裁定 15s，照抄 plan 派工致执行者初版用错阈值）；引用冻结文档的数字/口径，以 spec 为权威源。

```
待写spec → [文档子代理产 spec+plan] → 待评审 → [总控预审+按自治等级批] → 已批
→ [执行者分支开发+自测] → 分支就绪（**收官≠已合并**——合并序未到=分支挂起待合并窗，总控派工/写依赖前提时严禁混用两词，实战实证把「收官」当「已合并」写进下游 spec 依赖前提致下游开工撞空） → [合并序到达走合并三步] → 已合并
→ [文档子代理初审 AC 对账] → 初审通过 → [总控终审=分级审查]
   ├─ 全过（无必须修复项）→ [关功能+批次置已关闭+调下一批]
   └─ 有问题 → [返工清单落盘+批次置「返工中」（任务档返工节）]
              → [执行者 master 追加修复 commit] → [总控复验]
                ├─ 复验过 → 重走终审 →（全过收尾）
                └─ 仍有问题 → 循环（批次保持「返工中」）
```

**铁律：初审通过必落盘，禁止跳步**——初审完成后必须**单独提交**置「初审通过」（哪怕终审紧随其后同轮完成），再置终态（已关闭/返工中）。跳步置终态=断流水线：中间态落盘是状态机完整性与审计要求，也是信号指针的指对象。

**审循环分工与周转**：
1. 合并信号到 → 总控 spawn **文档子代理初审**（AC 逐条对账+中文三级分级：必须修复/建议修改/仅供参考）。多批同到时初审子代理并行 spawn。
2. 总控**终审**=分级审查；多批待审时**批量终审**（总控单点吞吐是瓶颈，初审并行+终审批量把周转压到不阻塞开发）。
3. 审查报告落点=任务档返工节+批次表内嵌（单一事实源，不落散件 review 文件）；追溯链=代码归属注释→blame→领域文档→ADR→spec→任务档。
4. 全过关批调下一批；有问题出**返工清单** → 派执行者在 master 上追加修复 commit（小分支不值得）→ 总控复验循环。
5. 返工路由：**原执行者优先**（上下文优势），正忙由空闲执行者/机动返工位接；一个批次贯穿到底（开发+返工同窗口）；争议问题总控报用户仲裁（重大档）。
6. **合并不需要用户确认**（自测过即合，审查后置）。

### 3.6 B0 双拆：契约先行（窗口刚性强时的基座批再拆）

基座批可再拆两步：**契约批 B0-c**（目录结构+接口签名+类型定义+DDL+测试基座 helper，目标 ≤1h 合并）先行合并；**实现批 B0-i** 随后。契约批就位后下游批次即开工——各执行者对 **stub 占位** TDD 测试先行，真实现（实现批）合并后清退 stub。

- **判定准则**：满足「≥3 执行者并行 + 执行窗口刚性强（闲时窗限时）+ S3 技术设计冻结达**契约级精度**（接口签名/类型/表结构可直接照抄成码）」→拆；任一不满足→基座批整体串行（拆分管理成本＞收益）。S3 阶段即按契约级精度输出是本拆法的前置要求。
- **契约批审查强度**：=表设计终审级（同 3.1 基座批）——签名/类型/DDL 一错，下游全部返工。
- **stub 清退纪律**：stub 只许占位不许写逻辑；真实现合并后**删除 stub**+下游**全量重跑**测试（stub 上的绿是假绿）。
- **stub 占位示例（三门语言各一行）**：
  - **Go**：`interface` + stub struct 方法直接 `panic("not implemented")`（编译期强制实现契约）；
  - **Python**：`typing.Protocol` + `NotImplementedError` + mypy 校验（动态语言须类型检查器作契约执行器）；
  - **TypeScript**：`interface` + 方法 `throw` + `tsc --strict`。
- **aiteam 实战反例（引注）**：未拆契约批时，执行者先行段撞工程骨架缺失（go.mod 未合并）测试无法编译而空转——契约缺位的代价；拆出契约批后此类等待机制性消灭。

## 第四章 并行纪律

### 4.1 worktree 隔离

- 每执行者每批次独立 worktree+feature 分支，命名 `feat/{{COLUMN_CODE}}-{{BATCH_ID}}`。*此位填项目分支命名规则：栏目代码与批次号组合，如 `feat/col01-b1` 形态。*
- 批次状态回写/信号操作一律在**主仓路径**执行（worktree 内改 docs 会把状态变更带进 feature 分支）。
- 构建/测试在 worktree 内跑（验的是分支代码）；worktree 不进 git 的本地运行配置须从主仓复制且**复制对环境版本**——「复制错配置=子代理连库持续超时」是高频事故，开工前先验连通。

### 4.2 槽位资源预分配（对接 `aiteam resource register`）

并行执行者各领**槽位四件套**（总控在批次表/plan 预先定好，勿改勿共用）：登录账号/端口组/测试数据标识段/信箱身份。真相源=任务档槽位表，开工自助读+派工信号确认；跨端批次领多行。

- **登记防互踩**：端口/测试账号段/测试数据段一律先登记后使用——`aiteam resource register --type port|account|data --value <值或段>`（如 port=`8080`、账号段=`acct:1000-1999`）；**冲突全局拒**（服务端返回与在用资源的冲突详情）；用完 `aiteam resource release`；`aiteam resource list` 查全项目占用。
- **测试数据正交**：数据标识段各用各的（plan 定段）；测试**自造自清、只清自己标识域**——出现全表清空或清他人标识域=违规；基建夹具行同守此规（按批预分配段位，或统一收基座批建）。
- **造数可辨归属**：造数名带执行者标识前缀（防撞业务唯一约束，对拍归属一目了然）；**测试断言不依赖全局自增序列绝对值**（并行期多执行者同时在库造数，自增 id 跨批漂移是常态——只断言存在性/相对值/稳定身份列）。
- **登录态隔离**：独立登录账号按端分池（token/会话键/验证码键全分离），防互踢。

### 4.3 全局变更窗

- **并行期零 DDL/零全局产物变更**（DDL/生成器配置/种子行/权限类批量 DML 等全局性库操作）——全局产物已收口进基座批。
- 执行中确有需要：**立即回报总控排全局变更窗**（信号升级，block 级），窗口内**全员停写**；窗口计划属中档留痕报备。禁止自行做。
- **全局变更验证三件套=build+全量 test+check**：DDL/schema 类全局变更合入后必须三件套全过才算窗口关闭——**基线红是全局变更最经典的遗漏面**（测试常含表清单/结构断言，build 过≠test 过，实战实证加表未同步测试期望致 master 基线红，靠下游合并前置验证兜出）。
- **批次间同包同名文件 AA 冲突真实存在**：「httptest 进程内测试无共享冲突」的并行安全判定不覆盖两批各自新建同名文件的场景（实战：两批各自实现中间件撞 middleware.go）——标准处置=rebase 时按**顶层声明并集+import 去重+两套测试共存**合并，禁二选一丢弃。
- **后台任务类进程全局单实例**：定时器/队列消费者等随进程起的后台任务全项目只起一处（防双跑双发消息/双清数据）。

### 4.4 开场先问后动+反证自检（一切会话通用）

1. **先问后动**：任何会话开场，若用户指令不足以唯一确定角色与目标栏目/任务，先列出当前全部可动方向（在途任务〔他总控分管，勿接管〕/已闭任务返工/新任务立项）问清再动——覆盖一切角色未定的开场（含用户主动发指令时）。
2. **反证自检**：接到「启用/启动/继续 XX」类指令，先核该动作是否已由其他会话完成（git log/任务档批次表状态/`aiteam status` 三处对拍）——已完成则指令只能指向别处，禁止按「当前主线」默认归属就地开工。
3. **阶段跃迁当轮回写红绿灯**：任务状态跃迁（立项/冻结/批次派工/关批/阶段推进）发生时，**当轮**回写项目红绿灯头部与进度台账（进度记录档）再收工——红绿灯是所有新会话的开工第一读，陈旧状态会把后续会话导向错误现场。
4. **共享热点文件写纪律**（红绿灯/台账/批次表是多会话共同回写热点）：只动自己行；Edit 前必重读最新；提交前 fetch 验证远端；commit 前核对暂存区只含自己文件（逐文件 add，禁整仓暂存）；热点文件改完尽快提交。

### 4.5 隔离原则矩阵（互踩源→隔离原则）

| 互踩源 | 隔离原则 |
|---|---|
| 登录态/会话互踢 | 独立登录账号（按端分池，会话键全分离） |
| 造数归属不清 | 账号+数据标识双维度（前缀可辨归属） |
| 服务实例冲突 | 槽位端口组各自配（resource register 登记+冲突全局拒） |
| 测试数据竞态 | 标识段正交；基建夹具行同守或收基座批建 |
| 缓存/共享键 | 键维度含正交标识/会话键含账号；只读共享键启用前抽查 |
| 全局产物变更 | 收口进基座批；并行期零变更；意外走全局变更窗 |

### 4.6 VCS 适配：SVN 纪律对照

aiteam **软件本身 VCS 无关**（镜像=纯文件写入，CLI 零 git 调用）；本节适配仅方法论层，全篇以 git 为默认叙述。**隔离开发**交 using-git-worktrees 技能原生优先自行处理（git 团队）；SVN 等集中式 VCS 项目按常规自行组织独立 working copy（集中式天然多副本，每执行者各自 checkout）——不自制 SVN 技能（YAGNI）。仅纪律层四项 git↔svn 对照：

| # | 纪律 | git 形态 | SVN 等价 |
|---|---|---|---|
| ① | 合并序号制 | rebase+`merge --no-ff` 串行 | trunk 提交串行+后合并者 `svn merge` 解冲突（svn 历史不可重写无 rebase——分支吸收主干变更=反向合并） |
| ② | 暂存区核对 | add 后 `diff --cached` | 无索引区：commit 前 `svn status` 逐文件核对 |
| ③ | 提交前核远端 | fetch+log 对拍 | commit 前 `update`（冲突先解再提交） |
| ④ | 归档搬运 | `git mv` | `svn move` |

## 第五章 时间盒与 token 经济

### 5.1 时间盒

- **单批次目标 ≤8 小时会话时间**：到点未完=收尾写状态（任务档检查点+`aiteam send` 信号回报停滞点与原因）停下汇报，**不无限磨**；半成品不悬挂——把完成度写清等调度决策。
- 哨兵纯传呼机（不带 `--max-wait`，哨兵常挂纪律见 §1.4）——无「8h 同节奏」形态：流转停滞感知不靠哨兵超时，归 `scripts/watchdog.sh` 进程级巡检（会话失联/哨兵孤儿经消息链报告总控）+总控叫号制续作令；哨兵命中即 poll 分级响应后**立即重挂**，无「到点退出不重挂」路径。
- **阶段时间窗（可选）**：`aiteam window set --from/--to` 为各阶段配执行时段，`aiteam window now` 权威查询当前允许阶段（窗外=waiting 挂起非报错）；AI 软闸遵守不硬拦，配置随项目存服务端+看板可见。
- **闲时窗口策略**：写码+测试是 token 消耗大头，集中到低价新闲时窗显著降本——窗口内最大化开发产出，白天留审查/文档/编排等低耗活。配套纪律（aiteam 实战形态）：①窗口前把依赖链上的批次先关批（窗内不等前序）②开工前置放宽=**合并即开工不等关批**（审查后置，返工由下游 rebase 吸收）③时间盒对齐窗口终点（到点收尾写状态，不悬挂半成品）④总控审循环周转压缩（初审并行 spawn+终审批量，见 3.5）。

### 5.2 总控禁机械产出

总控会话内**禁止机械产出型操作**——批量文本修改/文件搬运/格式转换/长文档起草，一律派子代理（机械类→cheap-model，判断类→文档子代理），总控只下指令+收一句话结论+终审。

**例外（封闭清单不得扩大）**：① git commit 收口（串行纪律要求单点）② 短 Edit 状态回写（审查结论的措辞即判断本身）③ 只读验证命令（终审取证）。

**自查信号：发现自己在写循环/正则/搬文件 → 停下改派。**

### 5.3 三档模型分配（按判断密度花钱，不按代码/文档形式分）

| 档 | 干什么 | 为什么 |
|---|---|---|
| **cheap（便宜档）** | 机械实现：规格已定的图绘制/成文/归档搬运/批量排查粗活 | 规格已定，判断密度≈0 |
| **standard（标准档）** | 集成判断：常规实现子代理（按 spec 施工+对照 AC）/文件审读/初审对账 | 既定框架内判断，密度中 |
| **strongest（最强档）** | 架构审查：总控终审/技术设计/spec 起草等方向载体 | 错了全错，判断密度最高，贵 token 花在刀刃上 |

- cheap-model 子代理须在客户端子代理注册处**事先注册**（注册表按会话启动加载，注册后需新会话可见）；不支持多档的客户端降级口径=全同档可跑（流程不依赖档位差，档位只影响成本）。
- 注册步骤与各客户端配置详见[接入指南](../../接入指南.md)会话编制节。

## 第六章 文档元规则（本档及下游文档修改规约）

1. **改规则=重写该步全文**：修订任何条款时整步/整节重写成文，**禁止括号补丁式注记**（「（2026-XX-XX 修订=…）」类累积注记是文档膨胀的根因——新旧口径并存比旧口径更误事）。
2. **实发教训一律进记忆库不进正文**：正文只留现行规则+条款级依据注；案例细节、复盘叙事归项目记忆库/复盘档——正文塞教训会让规则书变成事故集，新会话抓不住现行法。
3. **规则歧义=OQ 呈用户不自裁**：修订中发现规则歧义/矛盾/拿不准的，列入 OQ（open question）清单回呈用户裁决，禁止总控自行拍板写入——方法论的解释权归用户。
4. **模板只引条款号不复制规则**：下游文档（阶段模板/任务档模板/执行者契约）引用本总纲处只写章节号，规则正文以本档为唯一源——多处复制必然漂移。
5. **确认记录外迁**：本档=通用型方法论，全篇不记具体栏目号/任务名/项目细节（aiteam 引注除外，且只写通用流程形态）；新的用户确认记录一律追加到项目决策账本或确认档案（编号+日期+事项+结论）。

### 7.1 S7 归档流程（两分派工+收口链）

- **业务流程图=必备归档件，不许豁免/延后挂维护清单**：图源=验收版 PRD+实际实现（+验收证据）；场景分图 general/exception 按需拆；仅导出环境缺失属客观条件（先落源文件登记、后补导出，不算豁免）。
- **用户文档截图闭环**（有用户文档站的项目适用；无则跳过）：成文时标 `<!-- TODO-截图: 描述 -->` → 环境持有者真机实拍补齐 → 构建绿验收。
- **栏目收口链**：总控写关闭信号 → 执行者退役（退哨兵+退出全部自己起的后台服务，防僵尸进程）→ 信号档案随档归档（git mv / svn move，见 4.6④）→ 红绿灯/进度台账当轮回写 → **栏目不复用**（新栏目新会话新信号，序号从 1）。
- 总控复核（只读）→ 用户抽查，收口完成。

### 7.2 文档资产五层

| 层 | 载体 | 纪律 |
|---|---|---|
| ① 术语表 | CONTEXT 类术语档（大白话解释黑话） | 新术语**当场沉淀**，不等收口 |

### 7.3 spec 必备四节与台账铁律

- **spec 必备四节**（写/审 spec 逐节核对，缺即退回）：①旧链清退盘点（死代码删除）②结构影响评估（文件归位拆分）③往返账预估（N+1 批量化）④**资产回写盘点**（本批改了哪份领域文档/是否新 ADR/新术语/用户文档）。*spec 模板补「资产回写盘点」节与本档联动（aiteam 开发批次 b7a-3，前向引用：[spec-template.md](./spec-template.md) 编制中）。*
- **台账铁律**：无清单按 0% **禁估算**（进度=已完成项/总项，不是感觉）；**有条件通过不算完成**（带病合并不折算进度）；**状态一变谁执行谁回写**（当轮回写不过夜）。
- **S5~S7 模板诚实口径**：未实际走过的阶段，模板以「以你项目实况回填校正」诚实条款标注规划态，明写规划态与实况态差别——不假装已验证。

### 7.4 S7 后棕地演进轻流程（迭代收口后的再开发）

- **S7 收口≠方法论终点**：迭代归档后的再开发=棕地演进，**不走全 S0~S7**——规划件以既有冻结资产（立项档/PRD/技术设计）为基线增补，按需走轻流程：requirement-grilling（需求追问）→ brainstorming（方案构思）→ spec-review（spec 预审五项检查）→ writing-plans（执行计划）→ TDD 实现；每环节**以 Skill 工具加载对应技能**后按其流程走（不是凭记忆复述技能内容）。
- **产物口径不变**：spec/plan 照常落 `specs/<迭代>/` 并在 INDEX.md 登记行（状态与批次表一致），迭代收口整族归档 `specs/archive/<迭代>/`；PRD 级基线变更不适用轻流程，仍回全流程走 S2 冻结批审批链。

## 第八章 栏目间并行

### 8.1 适用范围

- **三支柱仅并行场景生效**：8.3 文档段上限/8.4 硬门槛解锁/8.5 开工前重审，仅多栏目并行时生效——单栏目正常开发走 S0~S7 原流程，S3 冻结两级审批链后正常进 S4，无「只能做文档」限制、不叠加重审。
- **两层并行正交**：第四章=同栏目内多执行者的并行纪律；本章=多栏目各自的完整流水线并行，叠加时同时遵守（栏目内按第四章组织执行者，栏目间按本章隔离）。
- **编制与适配纪律通用**：8.2 编制形态、8.6 配套适配单栏目同样遵守。
- **信箱一律栏目维度隔离**：无论是否并行，每栏目独立 `{{COLUMN_CODE}}` 收发信箱（1.4 逻辑信箱=column+role，role 命名规约全栏目统一），禁多栏目共用同一 column 收发。
- **产品衔接**：启用栏目并行先做两层登记——`aiteam project register`（项目级）+ `aiteam column register`（每栏目一条）；此后信箱/信号/资源登记/看板按栏目维度天然隔离。

### 8.2 编制：每栏目独立成套

- 每个并行栏目**独立成套**：1 个总控会话 + N 个执行者会话（执行者数量按 3.2 依赖判定三步法+3.3 执行者模式决策表判定）。
- 各栏目**互不共用会话**：不跨栏目共享执行者，不让一个总控兼管多栏目——总控上下文承载本栏目全量现场，兼任=多栏目现场互相污染。

### 8.3 并行范围上限=纯文档段

- 并行栏目可完整推进 S0 立项→S2 PRD 冻结→S3 技术设计冻结；spec/plan 等全部批次文档均可提前产（3.4 提前产文档模式，「预期态」标注纪律同）。
- 提前产文档的冻结批照常走对应审批（2.3 自治等级定落点），并行不降低任何冻结批门槛。
- **S4 起任何代码不写**：不建分支、不碰 worktree、不跑代码生成器/脚手架——并行栏目的代码动作由 8.4 门槛唯一解锁。

### 8.4 代码开工=硬门槛解锁

- 写代码的**唯一条件**=本栏目对前序栏目的依赖门达成（形如「本栏目开工=栏目 A 过 S6 业务验收」）。
- 门槛未到，文档再全也不开工；门槛达成也**不自动开工**——先过 8.5 重审。

### 8.5 开工前强制重审+修复（核心保险）

- 门槛达成后、进 S4 前，**本栏目总控**对并行期提前产的**全部文档**（立项档+PRD+技术设计+spec+plan）做预审级重审（口径同 S3 两级审批链的预审），专项抓两类：
  - **漂移**：并行期写文档时前序栏目仍在演化，文档中的「预期态/依赖产物引用」可能过时——逐项与实况对拍；
  - **质量**：提前产文档自身的设计缺陷/反前提（前序栏目实况可能推翻写作时假设）。
- 发现问题**先修文档，审过才开工**；写文档的会话（文档子代理）与重审的总控天然分离=双保险。

### 8.6 配套适配（只写栏目间增量；通用纪律见 4.2/4.3/4.4）

- **信箱按栏目分段**：命名空间=8.1 的栏目登记——每栏目独立 column 维度收发，跨栏目无信箱通道。
- **红绿灯门禁表述精确化**：并行期项目红绿灯〔项目状态速览档，见 2.3〕的并行栏目行写精确门禁=「文档段可做+代码段等门槛+开工前重审」，禁笼统「不得开工」；冷启动引导补并行栏目分支（新会话被问角色时按栏目号指路）。
- **槽位段位按栏目错开**：4.2 槽位四件套+`aiteam resource register` 冲突全局拒之上，端口组/测试数据段按栏目依次递增段位（后续栏目不复用既有段位），账号池按栏目建。
- **后台任务单实例的跨栏目归属声明**：4.3 全项目单实例原则下，归属声明行落项目红绿灯共享区（形如「后台任务当前归属=栏目 B 某执行者槽位」）；**跨栏目协调不走信箱**（信箱严格栏目内隔离），用户传话兜底；归属变更由起停方总控当轮回写共享行。
- **热点文件跨栏目增项**：4.4 共享热点写纪律之上，并行期增项=冲突**解不动他栏目行**——跨栏目边界争议按 2.2 重大档报用户，不代改他栏目内容。
- **交叉验证兜底记档**：执行者环境故障时，可用他栏目执行者环境交叉走查救场——记档备查，非默认动作。

### 8.7 触发语义与开场防歧义

- **「启用栏目并行」类指令的语义**：用户说「启用栏目并行/再开一个栏目并行」等，指**为尚未立项的新栏目开总控会话、从 S0 文档段起步**（8.3 范围上限）——在途栏目各有其总控（8.2 独立成套），新会话不接管、不兼管。
- **开场先问后动+反证自检**：按 4.4 通用纪律执行；并行场景增量=开场可动方向清单必含「为新栏目开并行总控」，反证自检的对拍处加核各栏目任务档状态。
- **阶段跃迁当轮回写红绿灯**：按 4.4 执行；并行期各栏目各自当轮回写、只动本栏目行——红绿灯陈旧会把其他栏目的新会话导向错误现场。

### 8.8 启用前验证清单（三件，约半天；仅项目首次启用并行，第二个并行栏目起不重复）

1. **运行时槽位双开共存**：两个执行者槽位（各端运行时实例成对）共库同跑；抽查缓存键维度含正交标识（4.5）；**后台任务双跑确认**——据实确定单实例载体落点（原则见 4.3）。
2. **账号池统建+会话分离验证**：按端建账号池，各自登录+各跑一条动线验证会话键分离（4.2 登录态隔离）——一次建好全项目共用。
3. **槽位分配落文档模板**：总控 spawn 文档子代理的任务书新增必带项=每执行者的槽位四件套（4.2）分配表。

## 第九章 纪律账：多会话协作条款

> **定位**：本章是多会话并行开发实践沉淀的纪律条款集（纪律账）——每条按「现象→条款」组织：现象用 1~2 句场景化描述（「并行开发中某会话……」「多会话共享工作区……」形态），条款全部场景化表述、可直接执行、可逐条对账。本章是既有章的实战细化，不替代既有章。

### 9.1 共享工作区与版本纪律

> 场景域：多会话共享同一工作区与版本库时的写入归属、落盘完整性与提交卫生。

- **热点文件并发写入**——并行开发中某会话向共享文件追加内容后未及时提交，另一会话提交时把前者的未提交行一并带入版本历史，文件归属与提交批内清单错位。
  1. 修改共享文件后**尽快提交**，把未提交窗口压到最小，不带未提交行跨轮工作。
  2. 提交前独立一步 `git diff --stat --cached` 逐行核对，暂存内容必须与本次目标完全一致；逐文件 add，禁整仓暂存。
  3. 发现把他人行带入版本历史，**立即出勘误回执**（回退剥离+知会受影响方），不静默放任错位历史。

- **校验与提交同链**——把核对命令与提交动作写进同一条复合命令，看到核对输出时提交已发生，核对失去拦截意义。
  1. 验证/核对类命令**永远独立调用**，永不与写操作串进同一复合命令链。
  2. 流程序固定：核对在前单独一步，输出确认无误之后才执行提交；核对不过=停手处置，禁「先提交再补看输出」。
  3. 闸位必须前置：放在不可回退动作之后的核对不构成拦截——判断必须发生在下一写动作之前。

- **信号落盘不完整**——向信箱写入（第一步）后忘记提交（第二步），或变更落在 worktree 内未回主仓，接收方在版本历史中看不到信号。
  1. 信箱写入后**当轮提交**，暂存清单必含信箱文件本体——只写不提交=信号未落盘。
  2. worktree 内产生的共享文件变更由该会话收口时兜底迁回主仓提交；共享文件按「最后经手人负责收口」追责。
  3. 会话收尾自查：`git status` 工作区全净、共享文件变更全部提交、无未落盘的半途写入——半途变更留给下个会话=埋雷。

- **格式化字符转义**——含 `%` 的内容经 printf 拼接写入文件时被当作格式符处理，落盘内容变形。
  1. 写文件内容含 `%` 时改用 heredoc 追加，禁 printf 拼接承载任意内容。
  2. 写文件脚手架对内容做格式符防御（转义或改走替代通道），不依赖内容恰好不含格式符。
  3. 追加类写入后回读文件尾核对行结构，防黏连巨行/截断（追加写入首字符必须是换行，见 1.4）。

- **写入前工作区检查**——向共享信箱追加内容前，该文件已有他人未提交行挂在工作区，此时操作会把他人行卷入自己的后续提交。
  1. 追加前独立一步查看该文件 `git status`：工作区非净=先查明归属再动。
  2. 发现他人未提交行=**暂停写入等其收口**，不带着他人行继续自己的操作（与热点文件组互补：本组防自己卷入他人的行，热点文件组防自己的行被他人带入）。

### 9.2 信箱与哨兵运维

> 场景域：aiteam CLI 信箱收发、消费位点与哨兵挂载、后台值守进程的运维卫生。

- **后台值守进程残留**——宿主会话已结束，后台哨兵仍持锁运行或重复挂载产生多实例，导致信号误报或新哨兵锁等待。
  1. 挂载前先查态：`aiteam status` 核对锁活性与锁主进程——已有活哨兵不重挂；锁主会话已死的孤儿哨兵先杀再清锁后重挂。
  2. 会话终结时随终：收尾动作必须含退出全部自己起的后台进程与哨兵，不留无主进程占锁。
  3. Windows 环境清理 bash 族后台进程用 bash 内建 kill（taskkill 覆盖不到真实进程树）；重挂前必清陈锁。

- **序号分配冲突**——多写方同时手写共享账本的序号产生重号/跳号，读方按位点消费时错乱。
  1. 序号一律脚本取号（取全文最大序号+1），禁多写方手写拍号；有服务端递增序号设施（`aiteam send`）的优先走设施。
  2. 读方断言用序号∪行数双电平，单电平断言漏检重号/跳号。
  3. 读到重号按内容实际语义处置并勘误入账，不机械按序号丢弃。

- **消费位点初始化**——读方位点缺省取全库最大序号时，哨兵未挂载窗口期产生的信号被跳过，信号静默丢失。
  1. 时序纪律=**先挂哨兵后派工**：信号可能产生的时段哨兵必须已在值守，从源头消灭窗口期。
  2. 新会话首读与恢复现场一律全量复查兜底（`aiteam history --since-seq 0` 从头拉）；不假设缺省位点会自动补看历史——不确定时段的信号宁可重读不可跳过。
  3. 恢复现场位点不凭记忆重设：以服务端记账（`aiteam status`）为权威，记忆与服务端不一致时按服务端。

- **哨兵挂载方式**——后台哨兵用 shell `&` 挂在复合命令里，宿主命令结束时哨兵被牵连终止或无人认领。
  1. 哨兵用执行环境的后台任务机制托管：挂载调用独立成当轮最后一次工具调用，不与其它命令复合。
  2. 挂载参数两查再挂：信箱地址/消费位点逐项核对（默认纯传呼机不带 `--max-wait`；闹钟=故障兜底件，确需使用须留痕理由）。
  3. 幂等挂载：检测到已有活哨兵时自动退出不重复挂载（防多实例）。

### 9.3 派工与文档同步

> 场景域：总控派工指令的质量闸与冻结文档（技术设计/spec/README 类）的跟手性。

- **冻结文档与实现漂移**——数据表/接口/命令面变更后，引用它们的冻结文档未同步，下游按旧文档开发返工。
  1. 冻结文档内嵌的图表/字段表/示例**随变更当轮同步**，与实现同一轮提交。
  2. spec 保留「资产回写盘点」节（7.3）：本批动了哪份文档/是否新增 ADR/术语/用户文档页，逐项列明。
  3. 合并前对拍文档引用面：引用的表/接口/命令逐一与实况核对，失真=先修文档再合并。

- **派工指令质量**——指令指名的文件/行号/机制与仓库实况不符，执行者按指令落空；或批次合并后未当场发出下一批指令，下游空等。
  1. 指令发出前先核事实：引用的文件存在/行号实指/机制实存，禁凭记忆写指针。
  2. 批次合并的处置与下一批派工**同轮完成**，不留下游空等窗。
  3. 指令引用有误时由发出方勘误并入账（决策账本/检查点），不发无痕口头更正。

### 9.4 跨平台细节

> 场景域：Windows 等跨平台环境的命令示例与编码。

- **跨平台编码**——Windows 自带 curl 发送含中文的请求体时编码损坏，入库成乱码。
  1. 示例命令的请求体省略非 ASCII 内容（省略合法），示例命令不内嵌中文等非 ASCII 数据。
  2. 中文内容补录走 CLI 动线（如 `aiteam send` 参数直传），不走 shell curl 拼 raw 请求体。
  3. 跨平台示例命令在平台差异处（路径分隔/引号/编码）分行标注适用平台，不写「各平台通用」的含糊示例。
