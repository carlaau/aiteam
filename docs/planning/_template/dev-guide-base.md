## 一、项目哲学（所有纪律的上位原则）

1. **代码 > 模板 > 文档**。文档是愿望，不是实际行为。三层信息冲突时以实际代码为准，
   模板/脚手架次之；改行为必须落到代码上——只改文档不改代码，等于没改。
2. **读穿数据流再下结论**。定位问题、评估改动面，必须端到端读穿实际链路：
   入口（CLI 命令 / HTTP handler / 页面事件）→ 请求入参字段 → 业务逻辑消费 → 存储（SQL 条件 / 写入路径），
   逐层实证找到唯一断点，再下结论、再提改法。只读切片、只看一端、凭记忆或文档推断 = 违规。
3. **结论越顺越主动找反证**。一个结论处处顺畅、毫无阻力时，警惕是自己想顺了：
   下结论前主动找反例（另一处调用面、边界分支、并发时序），找不到反证才收结论。

## 二、语言与代码纪律（语言适配占位——按你的语言替换本节）

> 本节保留「格式门槛 + 静态检查 + 编译/构建检查 = 提交门槛」的思想框架与 2.1~2.3 小节编号骨架，正文按你的语言替换。
> **Go 项目无需改造本节**：可直接参考 aiteam 仓自身 Go 版 `docs/dev-guide/base.md`，本节各「Go 版示例」块即摘自该版。

### 2.1 格式与检查门槛（提交门槛）

按你的语言选一套工具链，填入三个占位命令，三条合起来构成提交门槛：

- **提交前必跑 `{{FORMAT_CMD}} <改动的文件>`**（*此位填格式化命令及缩进风格，如 `gofmt -w`（Tab 缩进）/ `ruff format`（4 空格）/ `eslint --fix`（2 空格）*）——不跑就提交 = 违规。
- 提交前 `{{STATIC_CHECK_CMD}}` 与 `{{BUILD_CHECK_CMD}}` 必须零报错（*此位分别填静态检查命令与编译/构建检查命令，如 `go vet ./...` + `go build ./...`、`ruff check` + `pyright`、`tsc --noEmit`*）。

**三门语言适配示例行**（常见搭配，**按团队实际工具链替换**）：

| 语言 | 格式化（提交前必跑） | 检查门槛（零报错） |
|---|---|---|
| Go | `gofmt -w <文件>`（Tab 缩进） | `go vet ./...` + `go build ./...` |
| Python | `ruff format` / `black` | `ruff check` + `pyright` 零报错 |
| TypeScript | `eslint --fix` | `tsc --noEmit`（Vue 项目加 `vue-tsc`）零报错 |

> 解释型语言没有编译步骤的（如 Python），以「静态检查/类型检查零报错」充当第三条门槛，**不许空缺**。

### 2.2 语言写法纪律（占位）

- 通用总原则先立住：**按需 + 风格一致**——不是「优先用新特性」，更不要为用特性去重构存量结构。
- 在此填你的语言的现代写法/惯用法对照表（{{LANGUAGE_IDIOMS}}，*此位填惯用法对照表或指引其落点文件；形态参照下方 Go 版示例：「场景 → ✅ 用 → ❌ 不用」三列表，并注明不可机械套用的循环类例外判定*），新代码硬性遵循，存量勿为用新特性而改造。

**Go 版示例**（摘自 aiteam Go 版 §2.2；以下至本小节结束均为 Go 专属示例）：

| 场景 | ✅ 用 | ❌ 不用 |
|------|-------|---------|
| 空接口 | `any` | `interface{}`（注释与文档示例同步） |
| 排序 | `slices.Sort / SortFunc / SortStableFunc`（比较用 `cmp.Compare`） | `sort.Strings / sort.Slice / sort.SliceStable` |
| 成员查找 | `slices.Contains` | 手写 for + break |
| 固定次数循环 | `for range n` | `for j := 0; j < n; j++`（j 未用时） |
| 索引循环 | `for i := range len(s)` | C 式三段 for（i 无手动推进时） |
| 字符串截断 | `strings.Cut / CutPrefix / CutSuffix` | 手写 Index + 切片循环 |

**例外**：tokenize/parser 类循环体内有 `i = j-1` 手动回跳或 `i++` 跳字符的，**不可 range 化**（range 循环变量每轮重置，体内修改无效），保留 C 式 for 是正确的。

**泛型使用原则**：泛型方法无法被接口描述，业务逻辑层回避；工具层可用，但**纯映射不藏 IO**——泛型函数/闭包体内不夹查询、写库等副作用，夹了 IO 的保持手写 for。

## 三、结构治理

### 3.1 功能域分文件，防巨石

- 同一类型/模块的方法**不再默认塞同一文件**：一个文件超过约 {{SPLIT_THRESHOLD}} 行（*此位填拆文件行数阈值，基准口径约 500*）或出现第三个功能族时，按功能族拆文件（如把 `item` 相关代码拆出 `item_expand` / `item_delta` 两个功能族文件）。
- 新函数先问「属于哪个功能域文件」，再落笔；同包/同模块内同类方法分散在多文件无技术障碍（多数语言按文件组织源码，构建期自动归并）。
- 设计文档（spec/plan）新增函数/方法必答**「结构影响评估」**：目标文件现多少行 + 本任务净增多少 + 是否新功能族 → 放原文件还是拆新文件（写明理由）。

### 3.2 文件行数红线

- 实现文件**软上限 {{SOFT_LINE_LIMIT}} 行 / 硬上限 {{HARD_LINE_LIMIT}} 行**（*此位填行数红线两道阈值，基准口径软 800 / 硬 1000*）；测试文件豁免。软超限 = 提交时 WARN（触及该文件的提交应顺带拆分）；硬超限 = 阻塞提交。
- **红线超标唯一出口 = 按功能域拆文件**。禁止压缩排版（长签名/多语句/三元链挤一行）、禁止删注释来满足红线——两者按缺陷计，审查发现一律打回重拆。
- 度量按**有效代码行**（剔空行/注释行）：让「压行」「删注」在数学上无收益，防止为过红线走歪道。

### 3.3 旧链清退（死代码闭环）

- 凡「新链替换旧链」，任务必须包含收尾四步：**调用面盘点 → 调用方切流 → 调用清零 → 删除旧链**；确要保留（如外部调用方仍在）须显式记录原因，不许静默留下。
- **无引用即删，没有豁免**（项目若有代码生成器，生成产物以重生成/配置收敛处置，不适用本条）——死代码是迭代沉积物，不清即积累。
- 设计文档必含**「旧链清退盘点」节**：列出旧链调用面清单与逐项处置（删 / 保留+原因），收尾任务含对账步骤；缺失该节的文档审查退回。

### 3.4 拆文件与测试归组

- 实现文件拆分/改名时，对应测试文件跟随被测域改名，测试清单前后对账防丢覆盖。
- 两处高度镜像的代码（双胞胎结构）同步加功能时：公共逻辑**先抽共享文件**，行为差异**显式参数化**，禁止隐式分叉（两份代码各自长歪 = 口径漂移）。

## 四、数据访问纪律（N+1 防治）

> 无论你用哪种数据库——往返次数是通用成本，单行循环是通用反模式。

- **循环体内单行查库/写库默认违规**——先收集再批量化：IN 查询 + 内存组装、批量写语句，替代逐行 Get/Insert/Update/Delete。
- 确属逐行合理（后行依赖前行结果 / 量极小 / 逐行语义本身有意义），在循环行或函数 doc 加 `perf: per-row-ok <理由>` 标注（注释前缀按你的语言语法，如 `//` / `#`）；**无标注按缺陷计**。
- 装配/编排函数对同一存储对象多轮独立查询 → 合并一趟 IN + 内存重排。
- 设计文档涉及对同表 N 行读写（≥3 行循环形态）必含**「往返账预估」节**（预估往返次数与批量化的形态），缺失审查退回。
- 记住形态而非事后优化：**批量化是默认形态，逐行是须标注的例外。**

## 五、版本控制纪律

> **表头注**：git 主径；SVN 团队按总纲（[pipeline-overview.md](./pipeline-overview.md)）§4.6 四项对照表换算——对应关系：5.2 暂存面核对 ↔ 4.6②（svn：commit 前 `svn status` 逐文件核对）、5.3 fetch 验证 ↔ 4.6③（svn：commit 前 `svn update`）。
> 5.1 逐文件 add 为 git 暂存区工作流特有（svn 无暂存区；新增文件纳入版本控制用 `svn add` 同样逐个列出），svn 场景的提交前核对统一走 4.6②。
> 5.4 提交信息语言纪律 VCS 无关直接适用。

### 5.1 逐文件 add，禁止全量暂存

```
❌ git add -A      → 会把无关目录的 mode 变更、零字节改动全部卷进提交
❌ git add .       → 同上
❌ git add <目录>/  → 目录级通配也可能误加无关文件

✅ git add <具体文件路径>
✅ git add file1 file2   （多文件逐个列出）
```

### 5.2 提交前必须核对暂存面（多会话共享工作区防串味）

多个会话/成员并行操作同一工作区时，暂存区随时可能混入他人正在改的文件——commit 前必跑：

```
git diff --stat --cached    # 确认暂存区只包含本次目标文件
git diff --stat             # 确认工作区没有本会话的意外遗漏
```

发现无关文件：`git reset HEAD <文件>` 取消暂存，不要一并提交「顺手捎带」。

### 5.3 push 前先 fetch 验证远端

```
git fetch origin
git log HEAD..origin/<branch> --oneline    # 确认远端无他人新提交
```

远端有新提交（分叉）先 rebase/merge 解决再 push，禁止 `--force` 覆盖他人提交（误覆盖他人提交的修复流程代价远高于 fetch 一次）。

### 5.4 提交信息格式

```
格式：<type>(<scope>): <中文主题>
type:  feat / fix / refactor / docs / chore / test
scope: 按模块（如 server / cli / web / docs，以 S3 技术设计定名为准）
```

主题用中文，一行说清「改了什么、为什么」；多文件协同改动注明联动关系（如双胞胎同步、旧链清退收尾）。

### 5.5 协作拓扑纪律（`aiteam init` 自管区块）

> *本节由 `aiteam init --topology single|distributed` 按协作拓扑渲染成两口径之一的标记区块（`<!-- aiteam:topology:begin/end -->`）——重跑 init 区块内刷新、区块外零触碰；手动复制改造本档的用户删除占位符、自拟团队实际协作纪律。*
