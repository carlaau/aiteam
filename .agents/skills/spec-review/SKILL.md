# spec 架构预审：新手病拦截 + 用户终审减负

团队形态：新手同事 + AI 写 spec/plan → git 提交 → **用户（业务与架构最终把关人）审核**。
本技能在到达用户之前先做一道 AI 架构预审——用户不懂架构底层时产出的文档，最常见的病
不是写得差，而是**不知道系统已经有什么**（重复造轮子/无视既有约定/引用不存在的代码）。
这些病 AI 能查，用户不该人肉抓。

**只审不改**：发现问题写进报告让作者改，本技能不直接修改被审文档。

## 审什么（五项检查，按拦截价值排序）

1. **既有能力复用**（新手头号病）：设计要做的功能，系统是否已有？
   - 对照项目的领域现状文档（等于当前实现）与项目术语表；
   - grep 项目的字典/枚举配置（种子数据/配置表）、既有端点、公共组件；
   - 重点问：「这个引导用户输入的值，字典/配置能不能给默认？能不能派生/导入？」
     （反前提追问同 requirement-grilling 技能——铁案：一个「教用户手填参数」的
     设计被否决，字典默认值+后端预填即可，方案却全在教用户敲键盘）。
2. **项目约定与上位边界合规**：项目工程规范文档的强制规则（跨模块调用约定/镜像结构
   同步/提交纪律等）、分层纪律、缓存清理纪律、行数红线、语言与框架写法约定。
   **模块化任务另查上位边界**（项目模块规划目录内的 S0~S7 栏目）：spec 不得违反上位规划
   硬约束与模块 PRD 冻结的边界——下层覆盖上层=退回（要突破先回上层文档改，权威链见
   项目规划总纲）。
3. **事实核对**（读穿原则）：spec 里引用的每个文件路径/行号/字段/函数/端点，逐一打开
   验证实存且语义相符——新手+AI 极易引用幻觉出来的代码位置。
4. **四节完备**：旧链清退盘点/结构影响评估/往返账预估/资产回写盘点，缺节直接退回
   （项目工程规范硬门槛）。
5. **过渡态与风险自洽**：部署顺序、存量数据、竞态边界是否考虑到（参考项目踩坑/决策记录库）。

## 怎么审

1. 通读 spec 全文，列出它「默认为真」的所有前提，逐条过反前提检查。
2. 逐项跑上面五项检查，每项标注 PASS / 问题（分级：**必须修复**（方向错误/违反约定/
   事实不实）/ **建议修改** / **仅供参考**——对齐团队 review 惯例）。
3. 产出**大白话预审报告**（给用户看的，禁黑话）：

```markdown
# 《<spec 名》架构预审报告
结论：✅ 可交用户终审 / ⛔ 退回作者（N 项必须修复）
## 必须修复（逐条：问题/证据/建议）
## 建议修改 / 仅供参考
## 我核实过的事实清单（文件/行号/字段——你终审时可抽查）
```

4. 报告单独成文（或会话内输出），被审 spec 不动；退回时作者按报告修，再审走本技能。

## 流程衔接（两级审批）

```
同事会话：requirement-grilling → brainstorming → spec/plan（止步于此，状态=待用户审批）
        ↓ git push
AI 架构预审（本技能）→ 预审报告
        ↓
用户终审（业务方向拍板）→ spec 头部状态改「已批准」 → 才可执行 plan
```

- 执行任何他人产出的 spec/plan 前，先看头部状态：**非「已批准」不得开工**（项目提交前
  检查清单对账项）。
- 用户终审重点看预审报告+方向层（这活 AI 替代不了）；架构细节已被预审覆盖。
